# Deep Learning Integration — Codebase Findings

**Date:** 2026-08-11
**Status:** Investigation complete

## 1. Purpose

Before designing deep learning (DL) support, this document records what
already exists in Skyulf that DL can reuse, what's structurally missing, and
the constraints that shape the design in
[2026-08-11-architecture-design.md](2026-08-11-architecture-design.md).

## 2. Current Architecture Relevant to DL

### 2.1 Node registration (`skyulf-core`)

- `skyulf-core/skyulf/core/meta/decorators.py` — `@node_meta(id, name,
  category, description, params, tags)` attaches `__node_meta__` to a
  calculator class.
- `skyulf-core/skyulf/registry.py` — `NodeRegistry.register(name,
  applier_cls, metadata)` decorator registers a `(Calculator, Applier)` pair
  keyed by a string node id (e.g. `"random_forest"`). `get_calculator(name)`
  / `get_applier(name)` are the only lookup points used by the execution
  engine (`backend/ml_pipeline/_execution/engine/_node_runners.py:879-880`
  and `_schema_graph.py:95`).
- This mechanism is **generic** — it doesn't assume sklearn. A new DL
  calculator/applier pair can register under the same registry with no
  changes to the registry itself.

### 2.2 Modeling layer (`skyulf-core/skyulf/modeling/`)

- `base.py` — `BaseModelCalculator`/`BaseModelApplier` abstract classes
  define the contract: `problem_type` property, `fit(X, y, config,
  progress_callback, log_callback, validation_data)`, plus `extract_xy()` to
  split a target column out of a pandas/Polars frame or `(X, y)` tuple.
- `sklearn_wrapper.py` — `SklearnCalculator`/`SklearnApplier` implement that
  contract by wrapping any `sklearn.base.BaseEstimator`. `classification.py`,
  `regression.py`, `clustering.py`, `ensemble.py`, `naive_bayes.py` all
  instantiate `SklearnCalculator` with a concrete estimator class + default
  params + problem type, then `NodeRegistry.register(...)` it.
- **Implication:** DL needs an equivalent `DLCalculator`/`DLApplier` pair
  implementing the same `fit()`/predict contract, backed by PyTorch modules
  instead of sklearn estimators — everything above the wrapper (registry,
  node runners, job orchestration) is agnostic to what's inside `fit()`.

### 2.3 Engine abstraction (`skyulf-core/skyulf/engines/`)

- `protocol.py` defines `SkyulfDataFrame`, a `Protocol` any compute engine
  (pandas, Polars) must satisfy: `columns`, `shape`, `__getitem__`,
  `to_pandas()`, `to_arrow()`, etc.
- `pandas_engine.py` / `polars_engine.py` / `sklearn_bridge.py` adapt real
  frames to that protocol.
- **Implication:** tabular/text DL models can consume the same
  `SkyulfDataFrame`-conformant input as sklearn models (convert to
  `to_pandas()` / `to_arrow()` then tensorize inside the DL calculator).
  Image data is the exception — it doesn't fit a 2D dataframe model at all
  (see §3.3).

### 2.4 Data ingestion (`backend/data_ingestion/`)

- `connectors/file.py` — `LocalFileConnector.SUPPORTED_EXTENSIONS = {.csv,
  .xlsx, .xls, .parquet, .json}`, using `polars.scan_*` lazily for CSV/Parquet
  and eager reads for Excel/JSON. `connectors/s3.py` mirrors this for S3.
- No connector handles directories of files, images, audio, or arbitrary
  binary blobs. Every ingestion path assumes "load into a 2D frame."
- **Implication:** image (and to a lesser extent audio/video, out of scope
  for now) support requires a **new connector type** that does not produce a
  `SkyulfDataFrame` at all — it produces a manifest (file paths + labels)
  that a `torch.utils.data.Dataset` streams from at train time.

### 2.5 Existing text/vectorization pipeline

- `skyulf-core/skyulf/preprocessing/vectorization/` already has
  `count_vectorizer.py`, `tfidf_vectorizer.py`, `hashing_vectorizer.py`,
  `tokenizer.py`, and — notably — `sentence_embedder.py`.
- `sentence_embedder.py` uses the `sentence-transformers` package (see
  `requirements-nlp.txt`), which **already pulls in PyTorch as a transitive
  dependency**, just for embedding *inference*, not training. `torch` is
  effectively already "in the building" for NLP installs.
- `frontend/ml-canvas/src/modules/nodes/modeling/TextClassificationNode.tsx`
  is a task-scoped node reusing the generic `TrainingSettings` component,
  restricted to Naive Bayes/Logistic Regression/SGD (`tags: ["text"]` in the
  registry). This is the pattern a new `TransformerTextClassifier` DL node
  should follow.

### 2.6 Training execution & job orchestration (`backend/ml_pipeline/`)

> **Correction (2026-08-11, post rubber-duck validation):** the original
> version of this section incorrectly assumed `JobStrategyFactory`
> dispatches on *what runs inside* a job (i.e. by calculator type). Verified
> against the code: it does not. The real dispatch point — and the one that
> matters for DL — is one level lower, inside the pipeline engine.

- `_execution/job_manager_base.py` — `TrainingJobManagerBase` mixin: shared
  cancel/log/status-update skeleton. This layer only manages the `MLJob` DB
  row (create/cancel/status/list) — it never touches a calculator or model.
- `_execution/basic_training_manager.py` / `advanced_tuning_manager.py` —
  concrete managers for that DB-row lifecycle only.
- `_execution/strategies.py` — `JobStrategy`/`JobStrategyFactory
  .get_strategy_by_job` (`strategies.py:191`) dispatches **purely on the
  job's `run_mode` column** (`"fixed"` vs `"tuned"`) — it receives an `MLJob`
  row, never a calculator, so it structurally cannot "pick a manager based
  on calculator type" as originally assumed.
- **The actual fit-dispatch point is `_node_runners.py`'s `_run_training`**
  (`:497-533`): it resolves the calculator, checks
  `calculator.problem_type == "clustering"`, and only clustering calls
  `calculator.fit()` directly (`_run_training_direct`, `:535`). **Every
  non-clustering node — classification, regression, and (today) any DL
  model — is routed through `_run_training_tuned`
  (`:712`) regardless of `run_mode`**, which wraps the calculator in
  `TuningCalculator` (`skyulf-core/skyulf/modeling/_tuning/engine.py:271-357`).
  `TuningCalculator.fit` converts X/y to NumPy via `SklearnBridge.to_sklearn`,
  instantiates `calculator.model_class(**params)` (`engine.py:162-184`),
  fits/scores candidates through sklearn's CV/scorer machinery, and refits
  the best candidate (`_refit_best_model`, `engine.py:223-270` — which
  raises `"Model calculator does not have a model_class attribute"` if one
  isn't present). **A DL calculator's own `fit()` — the one that would run
  the epoch loop — is never invoked on this path.**
- Jobs are dispatched through Celery (`celery_worker.py`,
  `backend/ml_pipeline/tasks.py`), using a **solo pool** (one job at a time
  per worker), CPU-only, no GPU awareness anywhere in the stack.
- **Implication:** DL training needs **no new manager**. It needs a new
  direct-fit branch in `_run_training` — an `is_deep_learning` check
  alongside the existing `is_clustering` check — that calls the DL
  calculator's `fit()` directly, exactly the way clustering already does,
  bypassing `TuningCalculator`'s NumPy/CV/`model_class` machinery entirely.
  This also means: no `model_class` requirement, no CV-multiplied training
  cost, and no tuple-wrapped artifact from `_refit_best_model` for DL's
  `fixed`-mode jobs. "Tuned" (Advanced) mode for DL needs its own small
  Optuna-driven loop calling `fit()` per trial (see architecture design
  §4.3) rather than reusing `TuningCalculator`. The solo-pool constraint
  means a long DL job blocks the whole queue for its duration — worth an
  explicit CI/gate time budget (see roadmap).

### 2.7 Artifact storage (`backend/ml_pipeline/artifacts/`)

- `local.py` / `s3.py` — `ArtifactStore` implementations serialize
  everything with `joblib.dump`/`joblib.load`, appending `.joblib`
  unconditionally.
- **Implication:** PyTorch models don't serialize well through
  `joblib.dump` for anything beyond trivial cases (optimizer state, custom
  `nn.Module` subclasses, device placement). The artifact store needs a
  second format (`torch.save`/`state_dict` + an architecture descriptor) and
  a way to pick the right loader by artifact type, not just file extension.
  **Security note (verified):** `local.py:36-38`/`s3.py:131-134` already
  document that `joblib.load` uses pickle and can execute arbitrary code —
  `torch.load` carries the identical risk and must be called with
  `weights_only=True`, with the same warning carried into the new loader's
  docstring; this is not addressed by "load a state_dict instead of a whole
  model" alone.

### 2.8 Frontend node pattern (`frontend/ml-canvas/`)

- `src/core/factories/nodeFactory.ts` — `createModelingNode<Config>({type,
  label, description, icon, settings, defaultConfig, outputs})` factory used
  by every modeling node (`ClassificationNode.tsx`, `RegressionNode.tsx`,
  `TextClassificationNode.tsx`, `SegmentationNode.tsx`, etc.).
- `src/core/constants/stepTypes.ts` — `StepType` enum, mirrored exactly in
  `backend/ml_pipeline/constants.py`. All training-family nodes currently
  submit `StepType.TRAINING` with a `run_mode` discriminator; the backend
  doesn't need to know which canvas node produced the job.
- **Implication:** new DL nodes (`NeuralNetworkClassifier`,
  `NeuralNetworkRegressor`, `TransformerTextClassifier`,
  `SequenceForecaster`, `ImageClassifier`) can be built with the same
  factory, and — per the per-project rule about backend/frontend option
  duplication — every new dropdown/preset option added on the frontend
  (e.g. architecture presets, optimizer choices) must have a corresponding
  backend allow-list entry checked before shipping (see the repo's
  Backend/Core ↔ Frontend Sync Rule). **Additionally verified:** new
  frontend node `type` values must be added to `RUN_MODE_TRAINING_TYPES` in
  `frontend/ml-canvas/src/core/utils/pipelineConverter.ts:29-34`, or the
  converter will never recognize them as training nodes and they won't
  serialize to the backend's `training` step at all — a second,
  easy-to-miss sync point beyond the hyperparameter-enum one. See the
  dedicated [frontend design doc](2026-08-11-frontend-design.md) for the
  full, code-grounded UI/UX proposal.

### 2.9 Infra / compute environment

- `Dockerfile` — `python:3.12-slim` base, CPU-only, single-stage worker/API
  image, no CUDA toolkit, no GPU runtime flags in `docker-compose.yml` /
  `docker-compose.test.yml`.
- `pyproject.toml` optional-dependency groups: `geo`, `auth`, `viz`, `nlp`,
  `all` — no `dl` group yet. This is the established pattern for adding a
  new optional heavy dependency (PyTorch) without bloating the default
  install.
- **No GPU scheduling exists anywhere in the current stack.**

### 2.10 Ray migration (branch `080`, not merged, docs-only)

- `ray-migration/` on branch `080` contains 8 **approved but unimplemented**
  planning documents (no code — `backend/ray_jobs/`,
  `backend/ml_pipeline/_execution/backends/ray*.py` etc. don't exist on any
  branch yet). Target: replace Celery with Ray Jobs/Core as the compute
  plane, FastAPI + PostgreSQL remain the control/state plane, S3-compatible
  storage becomes the durable data plane.
- Directly relevant to DL: plan `04-distributed-compute-plan.md` defines
  `ResourceSpec(num_cpus, num_gpus, memory_mb)` and
  `resource_spec_for_job(job_type, settings)`. **Verified detail the
  original draft got wrong:** this function only branches on
  `job_type in {"tuning", everything-else}` and returns a single **global
  static** `settings.RAY_ENTRYPOINT_NUM_GPUS` for every non-tuning job
  (`04-distributed-compute-plan.md:179-190`) — there is no `"dl_training"`
  job type and no mechanism today to give an image job `num_gpus=1` while a
  tabular MLP job gets `num_gpus=0` in the same deployment. Reusing this
  for DL means **extending** `resource_spec_for_job`, not just calling it.
- Plan `01-execution-backend-foundation-plan.md` establishes a
  backend-neutral submission contract (`EXECUTION_BACKEND=local|celery|ray`)
  that DL training should target instead of coupling directly to Celery.
- **Implication:** rather than building a second, DL-specific GPU-scheduling
  layer, the DL training path should be written against the same
  backend-neutral execution interface. GPU *scheduling infrastructure*
  reuses Ray, but per-job GPU *differentiation* (image/transformer jobs
  needing a GPU, tabular MLP jobs not needing one) requires real, scoped
  extension work in the Ray migration's own code — it does not "fall out for
  free," and Phase 5 of the roadmap is scoped accordingly.

## 3. Key Constraints Shaping the Design

1. **No GPU today.** Any DL phase that meaningfully needs a GPU (image
   models, larger transformer fine-tuning) must degrade gracefully to CPU
   (e.g. transfer learning with a frozen backbone + small trainable head,
   ONNX Runtime for inference) and must not block on the Ray migration
   landing first — but should be *structured* so it benefits automatically
   once Ray + GPU scheduling exist.
2. **No epoch/batch training-loop concept exists.** This is the single
   biggest structural gap — every other piece (registry, artifact store,
   frontend factory, job status) can be extended incrementally; the training
   execution model needs a genuinely new component.
3. **No non-tabular data ingestion exists.** Image support is a new data
   modality end-to-end (upload, storage, connector, dataset abstraction) —
   it is correctly the highest-effort, last-delivered phase.
4. **Frontend/backend option duplication risk.** Per the repo's own sync
   rule, every DL node's architecture presets, optimizer choices, and
   hyperparameter enums must be hand-verified against backend allow-lists —
   this has caused real shipped bugs before (`FeatureGenerationNode.tsx` /
   `InvalidValueReplacementNode.tsx` examples in the repo's own coding
   rules).
5. **PyTorch is already a de-facto dependency** (via `sentence-transformers`
   in the optional `nlp` extra), which lowers the marginal cost of adopting
   it as *the* DL framework rather than introducing TensorFlow/Keras as a
   second stack.
