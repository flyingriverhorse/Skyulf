Databricks model catalog

Choose a model by its behavior, then copy one of its models: entries into config/training.yml. This catalog covers all 16 regression and 18 classification choices in the project wizard, including voting and stacking.

Keep the surrounding version: 1, defaults: and your existing data, target, validation and layout settings from the training reference. Each example below replaces the models: mapping; do not concatenate the tuned and untuned mappings. In a competition, give candidates distinct names. In a multi-target project, retain each branch's target and feature settings.

The untuned example fixes the estimator configuration. The tuned example uses a deliberately small explicit grid to demonstrate valid YAML; it is not the full automatic search space. Validation/CV comes from defaults, not from a tuning.cv field. Read search strategies and ensembles for all strategy fields, nested CV, budgets, member parameters and wizard questions.

Reading defaults and search spaces

The parameter tables are generated from the same Core hyperparameter registry used by the wizard's build_model_spaces.py. They show key supported controls, not every parameter accepted by an upstream estimator. Core catalog default is the registered control value, not a promise about an omitted YAML field. The adjacent column is generated from the calculator's actual constructor settings. Library/resolver means the calculator delegates that default to the installed estimator or its composite resolver. For example, Logistic Regression registers max_iter=100 in the catalog but an omitted YAML value runs with Core's max_iter=1000. Random Forest has similar explicit Core overrides. Supply a parameter explicitly when reproducing a catalog setting matters. Core also injects its deterministic seed into compatible estimators when no seed is given.

Table literals use JSON notation (null, true, false); the explicit constructor column preserves Python source (None, True, False). Use YAML null, true, false in configuration. A table's default does not imply that all combinations of its controls are valid; solver/penalty pairs and estimator capabilities are still checked.

Grid and halving-grid use the compact grid column. Random, halving-random and Optuna use the richer finite-choice column when the wizard supplies its automatic space. The wizard writes these axes into the generated configuration. A missing or empty YAML search_space also asks the runtime to derive the Core space for the selected model, respecting its fixed parameters and ensemble members. For halving, the default resource is n_samples; a resource parameter cannot also appear in its search space. The strategy guide explains minimum/maximum resources and how to limit the full Cartesian grid. Large automatic grids, especially ensembles with several members, can exceed max_candidates before fitting. Use a bounded explicit space such as the examples below, or a random strategy with an explicit trial budget.

Weights, optional packages and execution boundaries

weight_column is a training workflow setting, not a constructor parameter. The column is removed from model features; weights must be finite, nonnegative, and have a positive sum in every fitted fold. Neighbor models do not accept row weights. Ensembles require every selected base model and the final estimator to support them. Metrics and threshold selection remain unweighted. An ensemble's weights controls member averaging and is a separate concept.

Every card's Spark/serving note describes the current admission policy, not proof that a particular saved artifact will pass it. Training these estimators uses local pandas/Polars data within the configured row/byte bounds; choosing Spark inference does not turn fitting into Spark ML training. Spark worker and pinned serving admission inspect a complete pandas-fitted artifact, exact model classes, preprocessing, schemas, runtime and saved state. An otherwise eligible model can still be rejected by its preprocessing or custom scoring rules. See Spark execution and serving rollout.

Optional XGBoost/LightGBM packages must be installed in training and inference environments. Installing a package does not extend the admission allowlist. Local fit/predict examples do not establish Spark, REST, or ai_query acceptance.

ridge_regression

Ridge regression. Task: regression. A linear baseline with L2 shrinkage, useful when numeric predictors are correlated or there are many modest signals. Scale numeric features before comparing alpha values.

Sample weights: Yes; configure the workflow weight_column.

Optional package: None beyond the standard Core scikit-learn runtime.

Spark workers / serving: Not admitted by the current Spark-worker/pinned-serving model allowlist; use local inference.

Parameters and defaults

solver "auto" 'auto' Solver to use in the computational routines.
fit_intercept true Library/resolver Whether to calculate the intercept for this model.
random_state 42 Library/resolver Seed used by the stochastic sag/saga solvers.

xgboost_classifier

XGBoost classification. Task: classification. An optional gradient-boosted tree model with row/column sampling and regularization controls. Useful for tabular interactions when the matching xgboost package is available in every runtime.

Sample weights: Yes; configure the workflow weight_column.

Optional package: xgboost.

Spark workers / serving: Not admitted by the current Spark-worker/pinned-serving model allowlist; use local inference.
