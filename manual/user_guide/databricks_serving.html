    Set up a model serving endpoint and SQL function

    When you need it

    This optional workflow deploys a concrete registered model version, then creates a Unity Catalog SQL function calling its endpoint through ai_query. The endpoint runs the saved preprocessing and prediction code. Callers supply the model's input features, including any features produced by upstream joins or aggregations. The function returns predictions; your application or SQL job owns source selection and destination writes.

    There is no extra default Bundle job. Run the steps below deliberately from a Databricks Python notebook, or render the DDL and run it in Databricks SQL. REST serving works independently of whether you create the SQL function.

    Choose how predictions are produced

    Path Runs where Use it for Cost model
    Batch score job, inference_mode: local One Python process on job compute Scheduled or handoff scoring of a bounded table Job compute while it runs
    Batch score job, inference_mode: spark Spark workers via mlflow.pyfunc.spark_udf; no endpoint Large scheduled scoring into Delta Job compute while it runs
    REST endpoint (this page) Databricks Model Serving Applications needing one request at a time Endpoint compute while provisioned; scale to zero is enabled by default
    SQL function with ai_query (this page) Model Serving, called from SQL Analysts, SQL jobs and dashboards querying the endpoint Endpoint plus the SQL warehouse or cluster

    The batch job never calls an endpoint, and the endpoint never writes the prediction table: an ai_query caller decides where results go, for example CREATE TABLE ... AS SELECT score_fn(...). Spark workers and endpoints both run the saved pandas pipeline on independent batches, so both admit only the steps and models listed in Spark scoring support.

    Additional built-in models, voting/stacking and eligible preprocessing recipes need the training evidence described in built-in recipes and model evidence. For an endpoint-only project, set defaults.admit_probed_custom_steps: true in config/training.yml before training. Spark and online-feature projects already enable it. prepare_pinned_endpoint recomputes the certificate from the exact registered package; changing a serving setting cannot admit an old model without evidence. Missing or changed evidence requires retraining and registering a new version. Inspect partition_probe.json in that training run: the model and built-in step records explain what was checked. Serving uses the same model_probed and apply_probed_builtin certificate actions as Spark.

    flowchart LR
    A["prepare_pinned_endpoint"] --> B["create_pinned_endpoint"]
    B --> C["require_pinned_endpoint_ready"]
    C --> D["query_named_records: REST"]
    C --> E["create_serving_sql_function"]
    E --> F["SQL SELECT with ai_query"]

    For entity-key requests, first prepare and publish the model's online features, then use the online setup commands on this page. Change traffic gradually through the separate daily rollout workflow.

    Raw-input models and optional prediction tables

    The model's saved input schema determines what callers send. If the complete pipeline was fitted on raw columns, its admitted feature generation and fitted preprocessing run inside the model. Callers do not repeat those transformations or create a merged feature table. Spark joins and historical feature-table calculations performed before that pipeline are not automatically included.

    Training does not require a prediction sink. Keep score_handoff: disabled and scoring_mode: manual for endpoint-only use; an output table name in configuration does not itself create a table. REST calls and SQL functions return results. A separate caller decides whether to publish them with a DataFrame write or CREATE TABLE ... AS SELECT.

    What to edit

    File or input Set before running
    deployment/requirements.txt The matching producer runtime
    PinnedEndpointSpec in your notebook Concrete version, endpoint and logging destination
    SQL function name A new UC function name for this release
    config/serving.yml for online lookup online_serving endpoint and actual publication identities

    Use deployment identities and access for the Bundle and the permissions below for REST/SQL.

    The command

    1. Inspect the model and prepare the endpoint

    Install deployment/requirements.txt with uv pip install -r in your notebook environment. Use the same Skyulf source runtime that packaged the registered model: admission checks source provenance, fitted artifact digest, partition safety, named input/output signature and nullable transport. Updating the local library does not silently upgrade an old model package. Repackage and register a new version with the intended runtime when necessary.

    Supported packages are certified local pipelines (including a selected competition winner) and model sets. Admission is stricter than “any MLflow model”. Spark-native models, stateful/batch-dependent preprocessing and native feature lookup envelopes are not automatically admitted by this bridge.

    Edit the explicit identifiers below. Use a separate endpoint and function name for each release so existing callers continue to use their selected version.

    from databricks.sdk import WorkspaceClient
from skyulf.integrations.databricks.serving import (
    PinnedEndpointSpec,
    build_serving_sql_function,
    create_pinned_endpoint,
    create_serving_sql_function,
    prepare_pinned_endpoint,
    query_named_records,
    require_pinned_endpoint_ready,
)

client = WorkspaceClient()  # Notebook workspace identity, never embed a token.
spec = PinnedEndpointSpec(
    endpoint_name="risk-v7",
    model_name="models.risk.customer_risk",
    model_version="7",  # Concrete numeric version, not @champion or latest.
    logging_catalog="ops",
    logging_schema="serving",
    logging_table_prefix="risk_v7",
)
endpoint = prepare_pinned_endpoint(spec, tracking_uri="databricks", registry_uri="databricks-uc")
print("Inputs:", endpoint.input_schema)
print("Outputs:", endpoint.output_schema)
print("Endpoint configuration:", endpoint.config)

function = build_serving_sql_function(endpoint, "models.api.score_risk_v7")
print(function.create_sql)  # Inspect complete DDL before creating anything.

    Preparation reads the registry but creates no endpoint or function. The generated SQL uses the inspected schema, not an independently maintained feature list. Fields must have simple names (letters, digits, underscores; no leading digit) and must be unique ignoring case. Reserved words are quoted. Supported primitive types are boolean, int32/int64, float32/float64 and string, including supported pandas/Polars aliases. Unsupported types fail before SQL execution.

    For CPU custom models, the helper configures telemetry_config with sampling_fraction: 1.0. Databricks creates the <prefix>_payload inference view over its managed <prefix>_otel_logs Delta table. A workspace may reject the ai_gateway.inference_table_config path; set logging_mode="ai_gateway" only for a workspace that supports it. The helper never falls back automatically. Retain the endpoint, concrete model version and payload view name together: registry aliases can move independently of logged requests. See serving observation setup, Databricks custom-model telemetry and fast inference tables.

    Payload logging and the inference table

    Logging belongs to the endpoint, not to the caller: every request that reaches it is logged the same way, whether it comes from REST or from an ai_query SQL call. Choose it with logging_mode on PinnedEndpointSpec, or with online_serving.endpoint.logging_mode in config/serving.yml; setup does not ask.

    logging_mode What Databricks creates in <logging_catalog>.<logging_schema> When to choose it Rollout and serving monitoring
    telemetry (default) Raw <prefix>_otel_logs, _otel_spans and _otel_metrics tables, plus a <prefix>_payload view over the logs. Every request is logged (sampling_fraction: 1.0). New projects; the custom-model telemetry path Databricks recommends Available
    ai_gateway A <prefix>_payload Delta table written by AI Gateway, plus usage tracking Your organization already standardizes on AI Gateway inference tables, or telemetry is unavailable Available; some workspaces reject this path for custom models
    disabled Nothing Callers store predictions themselves, for example with ai_query Rejected with an explicit error

    Both logged modes expose the requests as <prefix>_payload, which is what Skyulf reads. A rejected mode fails endpoint creation; Skyulf never switches to the other mode automatically, so the log location stays explicit.

    The payload view holds raw request/response records and arrives with a delay of minutes. The batch score job is separate: it never calls the endpoint and always writes its configured prediction_table.

    Serve without an inference table

    Set logging_mode="disabled" when callers own prediction storage, for example an ai_query job that writes its own table with CREATE TABLE ... AS SELECT score_fn(...). The endpoint is created with no telemetry or AI Gateway inference table, and the logging_* fields may be empty. Readiness checks then reject an endpoint that does log payloads. Daily rollout and serving monitoring read those payload logs, so they reject a disabled endpoint with an explicit error.

    Write your own prediction table with ai_query

    The SQL function from step 3 already wraps ai_query with the model's typed inputs: it sends numeric NULLs as NaN and nullable integers/booleans as text, so the saved imputation still applies (a bare ai_query would send a NULL number as 0). Every input row returns exactly one result; the endpoint never drops rows. A model with a fitted outlier step or PowerTransformer can return a result with an empty prediction, scoring_status = excluded and an exclusion_reason such as outlier:<step name> or invalid:<step name> (see rows that are not scored). Handle that case explicitly in the caller; do not treat the empty prediction as zero. Keep keys outside the call so results join back. call_sql() renders the call for a table alias:

    -- Full refresh
CREATE OR REPLACE TABLE gold.trip_scores AS
SELECT s.trip_id, s.pickup_month,
       models.api.score_fare_v7(`pickup_hour` => s.`pickup_hour`,
                                `trip_distance` => s.`trip_distance`) AS result,
       current_timestamp() AS scored_at
FROM bronze.trips s;

-- Monthly incremental: rerunning the same month replaces it instead of duplicating it
DELETE FROM gold.trip_scores WHERE pickup_month = 2;
INSERT INTO gold.trip_scores (trip_id, pickup_month, result, scored_at)
SELECT s.trip_id, s.pickup_month, models.api.score_fare_v7(...), current_timestamp()
FROM bronze.trips s WHERE s.pickup_month = 2;

    For one row per key, MERGE INTO gold.latest USING (<the SELECT above>) AS s ON t.trip_id = s.trip_id WHEN MATCHED THEN UPDATE ... WHEN NOT MATCHED THEN INSERT .... Replace the argument list with your function's real call_sql() output. These tables are yours: Skyulf monitoring reads its own prediction tables or the endpoint payload logs, not caller-written tables.

    2. Create the REST endpoint and check readiness

    ready = create_pinned_endpoint(client, endpoint)  # Create once and wait for readiness.

    Databricks builds the endpoint asynchronously. This helper polls for readiness using endpoint.spec.ready_timeout_s (3600 seconds by default), then returns the ready endpoint. It requires READY and NOT_UPDATING and checks the exact model version, workload and logging configuration. A failed native update or an API error remaining after the SDK's own retries propagates. The polling timeout does not interrupt an HTTP request already in progress: the injected SDK client's HTTP timeout and retry budget are separate. A ready response received from that in-flight request can complete the wait after the polling deadline. Configure the client's transport limits when elapsed request time also needs a tighter bound.

    If the wait expires, TimeoutError leaves the endpoint intact. Inspect the endpoint page and its build logs. Resume waiting for the same admitted plan:

    from skyulf.integrations.databricks.serving import wait_for_pinned_endpoint_ready

ready = wait_for_pinned_endpoint_ready(client, endpoint)

    For one immediate check without waiting:

    require_pinned_endpoint_ready(client, endpoint)

    Prediction and SQL enrollment use this immediate check. Do not repeatedly call creation: an existing endpoint name is rejected. The helper does not overwrite endpoints or change model aliases.

    The default is CPU/Small with scale-to-zero enabled. Idle endpoints can stop serving compute after the platform's inactivity interval, and the next request can incur a cold start. This is separate from SQL warehouse compute and billing. See Databricks custom model serving.

    For an inspected model whose only input is x: float64, a REST probe is:

    response = query_named_records(client, endpoint, [{"x": 1.5}])
print(response.predictions)

    Replace that example with all and only your model's input fields. REST records use native JSON scalars except fitted nullable Int32, Int64, boolean and Boolean columns: those use canonical strings (e.g. "42", "true") or None, matching the saved package. The SQL wrapper handles this encoding for you.

    3. Create the SQL function

    Use a Databricks Spark session and SDK client from the same workspace:

    create_serving_sql_function(spark, client, function)

    The helper checks endpoint readiness/version before submitting CREATE FUNCTION. It never uses OR REPLACE or IF NOT EXISTS: an existing function is an error, so a stale implementation cannot be silently reused. SQL creation errors are propagated without retries. After successful creation, rerun the SELECT below as often as needed; creation is not part of every prediction query.

    For a SQL warehouse, run require_pinned_endpoint_ready first and execute the printed function.create_sql in the SQL editor. This path requires a Pro or Serverless SQL warehouse; ai_query is unavailable on SQL Classic. Supported Databricks Runtime compute requires 15.4 LTS or later. Verify workspace/region availability in the ai_query reference.

    The SQL wrapper calls the endpoint name, not a UC model URI. The model version is checked at deployment, but an endpoint administrator can change it afterwards. Restrict endpoint management rights and retain one endpoint per model release. The SQL function cannot atomically enforce the version on each call. Run require_pinned_endpoint_ready before a controlled batch as an additional check.

    4. Call it from a table

    # These names stand for your existing table with the model's input feature columns.
expression = function.call_sql(table_alias="source")
print(expression)
scored = spark.sql(
    f"SELECT source.customer_id, {expression} AS result "
    "FROM analytics.features.customer_inputs AS source LIMIT 10"
)
display(scored)

    Copy the printed expression into your own SQL job. It uses named arguments, so source-table column order does not control feature order. The wrapper builds named_struct in saved model order and declares returnType explicitly. SQL arguments use the fitted types; nullable integer/boolean values are cast directly to canonical strings without a floating-point conversion. Their nulls stay null. For floating-point inputs, the wrapper represents SQL nulls as a same-width NaN before calling ai_query, so the saved preprocessing handles missing values. This prevents the numeric-null-to-zero behavior reproduced in native testing. It does not fill values with a new SQL-side mean or constant. Use matching source types: SQL's argument coercion is not a data validation layer.

    result is the named per-row prediction struct, not the REST predictions array. Its fields match endpoint.output_schema: e.g. result.prediction, probability fields, model-set outputs and saved project-scoring status fields when present. A single model, a registered competition winner and an admitted model set use the same SQL API; the saved output schema determines the returned fields.

    Set up an online Bundle endpoint

    First complete online Bundle training and publication. This endpoint setup job exists only when initialization selected include_online_serving: "true". It is unscheduled and never creates a publication.

    Take the concrete registered version from the training result and complete online_serving in config/serving.yml:

    online_serving:
  enabled: true
  exclusive_writer: true
  tracking_uri: databricks
  registry_uri: databricks-uc
  endpoint:
    endpoint_name: customer-online-v3
    model_name: models.risk.customer_online
    model_version: "3"
    workload_type: CPU
    workload_size: Small
    scale_to_zero_enabled: true
    ready_timeout_s: 3600
    logging_catalog: ops
    logging_schema: serving
    logging_table_prefix: customer_online_v3
    logging_mode: telemetry
  publications:
    - source_table: features.customer.customer_features
      source_table_id: "REPLACE_WITH_DESCRIBE_DETAIL_ID"
      online_table: features.online.customer_features
      online_store: customer-features
      publish_mode: TRIGGERED # Match the existing publication; use CONTINUOUS for a stream.

    Use actual resolved UC names here; the source table must be the model's saved lookup source with the same Delta identity. Configure exclusive endpoint writer permissions before setting exclusive_writer: true. The setup identity must be able to inspect the source, publication and store; the serving identity also needs access to the online features. Grant visibility of all publications for these sources and prevent concurrent publication changes during setup. UC enumeration covers the setup identity's visible inventory, not hidden resources. Setup rejects missing, mismatched or ambiguous accessible publications and requires evidence of a completed first sync before admitting creation. It reports a validation error while the first sync is incomplete; it does not poll or republish.

    databricks bundle deploy -t test
databricks bundle run online_serving_setup -t test

    The setup result reports READY, model_uri, input_schema and a typed request_example derived from the actual native signature. Replace its example values with a real entity and all other required request values, then send that request body to POST /serving-endpoints/customer-online-v3/invocations or use query_named_records in the SDK example below. Endpoint readiness does not establish that every requested entity has current features; the saved lookup policy checks that at prediction time. Rerunning setup never overwrites an existing endpoint. On timeout, inspect the existing endpoint and resume an explicit wait; do not rerun creation with the same name.

    Save the returned request_example object as request.json, replace its sample values, and query after the endpoint reports readiness:

    databricks serving-endpoints get customer-online-v3
databricks serving-endpoints query customer-online-v3 --json @request.json

    Required source metadata can survive in the native signature, even when excluded from estimator inputs. Inspect input_schema; do not assume every model accepts keys alone. Direct REST callers can override fetched values. Freshness validation checks the received values and does not attest their source.

    Endpoint compute and setup timeout

    These settings belong to online_serving.endpoint. They are also keyword arguments of PinnedEndpointSpec for a regular endpoint without online lookup.

    Setting Default Supported values and effect
    workload_type CPU CPU, CPU_MEDIUM, CPU_LARGE: CPU memory tiers. Availability depends on your Databricks workspace. GPU model packages are outside this setup.
    workload_size Small Small, Medium, Large: serving capacity. Larger sizes can cost more; choose using your measured traffic.
    scale_to_zero_enabled true A YAML boolean. Set false to keep serving compute provisioned while idle; true permits cold starts. Some workspaces require true; platform restrictions are returned as errors.
    ready_timeout_s 3600 A positive integer in seconds. Controls the setup wait only; it does not change request timeout or get sent as an endpoint setting.

    For example, to keep a Medium endpoint warm and allow 30 minutes for startup:

    workload_type: CPU
workload_size: Medium
scale_to_zero_enabled: false
ready_timeout_s: 1800

    Place those four lines under online_serving.endpoint. A changed YAML file does not update an existing endpoint. Setup is create-only: use a new endpoint name and explicitly move your callers after verifying it. A daily rollout must use the same workload type, size and scale-to-zero setting for champion and challenger; each plan can have its own client-side wait timeout.

    To seed these values during Bundle initialization, the answer-file keys are serving_workload_type, serving_workload_size, serving_scale_to_zero_enabled and serving_ready_timeout_s. All four are hidden from interactive questions but accepted in an answer JSON file. As with other initialization answers, use strings there (for example "false" and "1800"); the generated serving.yml contains typed booleans and integers. The generated setup job and task also have a total runtime cap, controlled by the existing Bundle variable monitoring_timeout_seconds (7200 by default). Keep that cap above ready_timeout_s plus model/publication inspection time. Increasing the wait in YAML alone cannot extend the Databricks job deadline. See Databricks endpoint configuration for the platform's compute and readiness behavior.

    Admit and query the registered package

    The following SDK route is an alternative to the Bundle's online_serving_setup job. Register the native outer package, then inspect a concrete version:

    from databricks.sdk import WorkspaceClient
from skyulf.integrations.databricks.serving import (
    PinnedEndpointSpec,
    create_pinned_endpoint,
    prepare_online_endpoint,
    query_named_records,
    require_pinned_endpoint_ready,
)

workspace = WorkspaceClient()
spec = PinnedEndpointSpec(
    endpoint_name="customer-risk-online",
    model_name="models.risk.customer_risk_online",
    model_version="3",
    logging_catalog="ops",
    logging_schema="serving",
    logging_table_prefix="customer_risk_online",
)
plan = prepare_online_endpoint(
    spec, tracking_uri="databricks", registry_uri="databricks-uc"
)
print(plan.input_schema)
create_pinned_endpoint(workspace, plan)  # Once, using a new endpoint name.

    After deployment is ready:

    require_pinned_endpoint_ready(workspace, plan)
response = query_named_records(workspace, plan, [{"customer_id": 42}])
print(response)

    The example request is valid only if the inspected input schema requires exactly customer_id. Native Feature Engineering can retain excluded training-source columns in its outer signature. Supply every field reported by plan.input_schema, or train from a narrower source. Temporal/date and binary source inputs are rejected by this bridge. The endpoint identity must have permission to read the required online features.

    The helper's exact schema excludes feature overrides. Direct native REST calls can still provide feature values, including a freshness value. The saved guard checks the values it receives; it cannot prove that those values came from the online store after enrichment. Restrict direct endpoint access or use an application boundary if your application must prohibit caller overrides.

    What you should see

    Validate your endpoint

    Compare direct saved-model, REST and SQL predictions using the same representative inputs. Include nulls, reordered named columns, integer limits and keys, and all component/composition outputs used by your application. Check strict and captured error behavior without treating an error result as a valid prediction.

    Use the actual caller identity to verify access rules. For classification, inspect labels and every probability column; for production capacity, measure cold starts, scale-to-zero behavior and sustained load. Recipe admission does not establish these endpoint-specific properties. Keep the concrete model version and request schema fixed during the comparison.

    Online monitoring enrollment is documented in serving observations and enrollment.

    Common errors and fixes

    Errors and privileges

    Default fail_on_error=True stops the query on an endpoint error. To inspect row-level endpoint failures, create a different function with capture enabled:

    capture = build_serving_sql_function(
    endpoint, "models.api.score_risk_v7_checked", fail_on_error=False
)
print(capture.create_sql)
create_serving_sql_function(spark, client, capture)

    This function returns {response: <prediction struct>, errorMessage: STRING}. On endpoint success, errorMessage is null. On an endpoint error, response is null. Authorization, SQL and other non-endpoint failures can still fail the whole query. Preserve and inspect errors before writing accepted predictions. See Databricks error behavior.

    • The deployer needs appropriate model/endpoint creation and logging destination permissions. Existing endpoint preparation also needs registry/artifact access.
    • The function creator needs USE CATALOG, USE SCHEMA, CREATE FUNCTION in the function's schema, and endpoint CAN QUERY; the SDK readiness check also requires endpoint visibility. The endpoint must be in the SQL workspace.
    • Function callers need USE CATALOG, USE SCHEMA and EXECUTE on the function, plus permissions for their own source reads, destination writes and compute. Databricks documents the ai_query definer's endpoint permission; verify the intended caller identity in your workspace before sharing the function.
    • Skyulf does not grant permissions or create catalogs/schemas here. An owner can grant EXECUTE ON FUNCTION models.api.score_risk_v7 TO ... explicitly.

    See Unity Catalog UDF permissions and SQL function creation.

    Symptom What to check
    Preparation rejects source/digest/signature Correct concrete model package and matching Skyulf runtime; do not bypass admission.
    Endpoint not ready/config mismatch Endpoint deployment state, build logs and exact version/configuration.
    Function already exists Use a new release name or deliberately manage the old function yourself.
    SQL permission/unsupported feature error Caller/definer privileges, warehouse/runtime and workspace preview availability.
    Missing field or type error Compare source fields with endpoint.input_schema; inspect SQL coercions.
    Row returns errorMessage Endpoint response/build logs; preserve the failed row for diagnosis.
    First invocation is slow Cold start and endpoint capacity; retry only under your workload's policy.

    For missing or stale online features, use the feature guard checks. For traffic decisions, inspect the daily rollout evidence.
