    Enroll models and run monitoring

    When you need it

    Use this page after store setup to enroll activated or scored batch models, prepare their references, and start observation. For endpoints, use serving monitoring.

    Monitoring writes to the shared store only for mode: production deployments (test, syst, prod). By default, personal development targets do not enroll temporary models or create monitoring tables: they set monitoring_enabled: "false", and the monitoring_allowed condition then skips enrollment and the post-scoring monitoring handoff. Training and scoring still run normally, including automatic scoring after activation. Development targets also set monitoring_performance_policies: '{}' and on_drift: disabled.

    Development monitoring (optional)

    To see your own development models, answer development_monitoring: "true" in setup. The question appears with personal development targets and needs a monitoring store; it defaults to off. Setup then asks for the schema name (development_monitoring_schema, default development_monitoring) in the same catalog. Any name works, including an existing schema in your workspace, as long as it is not the shared monitoring_schema. Every *_development target sets monitoring_enabled: "true", and every job receives both names. Change the name later in deployment/variables.yml; a blank name keeps development monitoring off.

    Core keeps the two stores apart: in development mode it writes only to development_monitoring_schema and refuses one that is missing or equal to the shared schema; test, syst and prod always use the shared schema. Development models are measured and reported only; automatic retraining stays disabled. Development jobs run as you, so you may need permission to create the schema, or ask for it to be created first. bundle destroy does not remove a development model's enrollment, so old trial models remain in the development store until you clean or recreate it. With monitoring_dashboard: create, test_development also gets its own dashboard over this store; development mode prefixes its name for each user.

    flowchart LR
    A["train: register_monitor"] --> B["score"]
    B --> C["prepare_monitoring"]
    C --> D["monitoring_ready"]
    D --> E["monitor_model: Run Job"]
    E --> F["monitoring job"]

    Activation enrolls the model in the train job. Each successful score then hands its receipt to the separate monitoring job.

    If monitoring is not configured

    Monitoring runs only when setup answered monitoring: "true", which sets monitoring_enabled: "true". monitoring: "false" sets it to "false": train and score run, register_monitor and prepare_monitoring report disabled, and the score job skips monitor_model. Nothing is enrolled or observed. Enable it later as described in store setup. A configured "false" flag with both names set publishes a pause instead. Without a configured label table, drift and feature quality still run; actual model performance remains unavailable.

    Keep model/data catalog, input_schema, output_schema and metadata_schema unchanged. After a successful activation, the train job's register_monitor task registers the version from the verified lifecycle result before scoring. The training graph orders training_report -> register_monitor before scoring_requested in every layout. Initial activation, approval and rollback are supported; pending/rejected candidates do not replace the active enrollment. Merely running bundle deploy does not activate a model. A successful scoring or CDF-recovery task also registers its actual model version and physical Delta prediction generation. It never resolves an alias a second time. No-op scoring also repairs registration without writing duplicate predictions. A registration error fails the task visibly; previously committed predictions remain intact and their receipt makes scoring retries safe. A pending recovery request does not register an output as successfully scored.

    What to edit

    In the generated model Bundle's target variables, configure:

    monitoring_catalog: operations
monitoring_schema: model_monitoring
monitoring_expected_interval_hours: "24"
monitoring_revisit_windows: "3" # Includes the latest completed window
monitoring_drift_thresholds: '{"psi": 0.2, "ks_statistic": 0.1, "wasserstein": 0.1, "kl_divergence": 0.1}'
# Optional shared MLflow experiment for the post-scoring task:
monitoring_experiment_name: /Shared/skyulf/monitoring
monitoring_dashboard_url: "https://<workspace-host>/dashboardsv3/<dashboard-id>/published"
# Optional actual results:
monitoring_label_table: outcomes.production.labels
monitoring_result_available_at_column: available_at
monitoring_performance_policies: '{}'

    Place this excerpt under targets.<target>.variables in the generated deployment/targets.yml. Performance and delayed labels are optional; choose their policy on the performance-loss page.

    The inventory holds the latest enrollment for environment/project/fully qualified model name. A newly scored model version updates that enrollment and keeps old version observations in history. It appears never_observed until the central job measures the new configuration. Removing deployment settings does not delete an existing enrollment. To pause, retain the destination, set monitoring_enabled to false and run scoring, or upsert a disabled MonitorConfig through enroll_monitor. Do not edit only the duplicated config/digest fields by hand. Removing only the destination while monitoring is enabled is invalid. External alias edits do not trigger enrollment.

    Automatic registration supports single models, competition winners and model-set components. Model-set activation enrolls each component's concrete version before scoring. Each component retains its parent set name/version/branch and reads its own predictions from the shared physical output table. Use all or separate_views; combined_only cannot supply individual model performance and is rejected before scoring when monitoring storage is configured. No JSON model list is required.

    The command

    Run from the generated project root after reviewing its target variables. These commands operate on Databricks; replace YOUR_PROFILE and the target. Deploy updated model, score and monitoring jobs together when changing their shared runtime contract.

    databricks bundle validate --strict -t test --profile YOUR_PROFILE
databricks bundle deploy -t test --profile YOUR_PROFILE
databricks bundle run monitoring -t test --profile YOUR_PROFILE

    Prepare references for a first pinned candidate

    Activation prepares verified training references. A first manual candidate scored by concrete version may be enrolled by scoring without having been activated. In that case, the prediction commit can succeed while the monitoring child fails with Spark reference is not prepared; run prepare_spark_monitoring_reference first. Open the score receipt to confirm publication, then run the existing monitoring job's preparation action for the enrolled identity:

    databricks bundle run monitoring -t test --profile YOUR_PROFILE --params monitoring_action=prepare_references

    Use the same project, target and monitoring namespace. Preparation reads the saved training evidence and creates/reuses the immutable references; it does not train, promote or rescore. After it succeeds, repeat the original score request to finish its monitoring handoff. An unchanged source/model replay is a prediction no-op; inspect the original commit and the separate child result. Do not delete output rows or invent a new watermark to repair monitoring. The preparation action needs the reference/table permissions of the shared store.

    After reference preparation succeeds, set monitoring_pause_status: "UNPAUSED" in the target variables and redeploy to let the existing UTC schedule revisit observations. Keep the generated schedule paused until references and permissions are verified.

    What you should see

    Generated producer Bundles always use Spark monitoring; no engine selection is required. Scoring validates its exact receipt, then a native Run Job task calls the independent third monitoring job and waits for its result. Training can call scoring through the same native job hierarchy. Monitoring uses its own serverless environment, timeout and retry settings, and a UTC schedule that starts PAUSED. Prepare and verify references before unpausing it. The scheduled run observes enrolled models and delayed labels even if no new scoring batch arrives. Its tasks run monitor_model -> monitoring_report -> evaluate_retraining; a guarded policy may submit the producer's complete train job.

    With monitoring configured and enabled, every successful scoring receipt reaches the dedicated monitoring job. Failed scoring and missing saved batches do not create a successful observation. Dashboard refresh reads saved results; it does not run monitoring and an already open page is not a push stream. Use the dashboard's refresh control to load new observations; reloading the browser can still reuse cached query results. Scheduled monitoring covers late labels even when scoring has not run again.

    Open monitoring_report for saved drift, observed performance and policy evidence; Open monitoring dashboard appears when the shared HTTPS URL is configured. evaluate_retraining then applies only explicitly enabled retraining policies.

    The score job runs prepare_monitoring -> monitoring_ready -> monitor_model, where the final node is the native child-job call. Calculation, saved drift reports and guarded retraining belong to that child job. The monitoring job's own monitor_model executes src/jobs/monitor_project.py; the scoring job's task with that key invokes the child job. All projects can link to the same monitoring_dashboard_url.

    For custom inventory-wide SDK runs, select a suitable observation window. The inventory limit bounds enrolled models, not prediction rows. Refreshing the dashboard does not compute new metrics. Each model failure is saved, other models are attempted, and the notebook then fails if any model failed. Inspect reports before retrying.

    Observation identity includes configuration, cutoff, window and snapshot evidence. Exact retries do not overwrite history. Current health ranks the newest window, then its latest measurement; historical backfills cannot replace newer windows. Keep the Delta retention needed for source replay and audit history.

    Library API and local execution

    The library can read a bounded inventory snapshot, default maximum 10,000 entries. The SDK can enroll explicit records and run inventory-wide observations; it does not require a configuration file or a second template.

    The public local API observes with pandas or Polars in the Python process. MonitorConfig.max_rows=10000 is its default observation budget; MAX_MONITOR_ROWS=1_000_000 is the local safety ceiling. The local byte budget defaults to 64 MiB and is capped at 1 GiB. Neither local row nor byte budget limits Spark observation rows. These are not two separate Spark limits.

    The observation budget bounds local data, while the inventory budget bounds enrolled models. Generated Spark observation rows have neither local row nor local byte caps; drift measurement limits still apply.

    Common errors and fixes

    If train or score fails with Set both monitoring_catalog and monitoring_schema., monitoring is enabled or one name is set alone; fix the destination as described in store setup. If nothing is monitored after successful scoring, check that monitoring_enabled is "true" for that target.

    A deployment alone does not activate or enroll a model. Run the normal lifecycle/scoring path, then check the concrete version and configuration in inventory. A configured false flag publishes a pause only when registration executes; removing configuration does not delete the previous enrollment.

    Reference preparation is a separate, one-time activation or explicit migration step. It replays the original training source under the existing bounded training row and byte budget, validates the original split and writes pinned reference populations. Models without monitoring_source_evidence.json need retraining or verified original source proof; the job never silently reconstructs provenance. Spark freshness checks fail explicitly for unsupported fixed normalizers, custom pre-split filters and custom weight generators. Supported source weight columns still obey the training contract. Training remains local even when inference is distributed. Spark monitoring does not change the training or scoring engine.

    Activation enrollment is ordered by the original serialized lifecycle run start. A delayed score cannot replace an activated different version, and repairing an older activation cannot replace a newer activation. Enrollment-only repairs read the verified original receipt without repeating training or alias changes. The private activation-order metadata lives in inventory config_json; table schemas and model configuration digests do not include it. Every job that reads the shared inventory must run a Core release that understands it.

    Current-health states and their freshness rules are described on Drift and data quality. If the latest report failed, inspect its saved error before retrying; the dashboard does not reuse an older success.
