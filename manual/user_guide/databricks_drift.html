    Measure drift and feature data quality

    When you need it

    Use drift to compare production inputs with the verified population used to train a concrete model version. It detects changed distributions, missing declared features and incompatible types without requiring outcome labels. Performance loss instead compares labeled prediction quality with a baseline. Both can independently qualify for guarded retraining.

    What to edit

    Set monitoring_drift_thresholds under the producer target's variables in deployment/targets.yml. These are the current defaults:

    monitoring_drift_thresholds: '{"psi": 0.2, "ks_statistic": 0.1, "wasserstein": 0.1, "kl_divergence": 0.1}'

    monitoring_drift_thresholds is authoritative for this project's enrollment; {} uses Core defaults and partial objects override named metrics. Defaults are PSI 0.2, KS statistic 0.1, normalized Wasserstein 0.1 and KL divergence 0.1. A value must strictly exceed its own threshold. The displayed KS p-value is diagnostic relative to these effect limits; statistical support is checked separately.

    Check Comparison and limit
    Numeric PSI Compare distributions using reference-derived bins; use psi (0.2). Low-cardinality numeric references use midpoint bins; otherwise reference percentiles supply the bins.
    Categorical PSI Compare category frequencies; use the same psi limit.
    KS Maximum empirical cumulative-distribution gap; compare KS statistic with ks_statistic (0.1). The diagnostic KS p-value is never compared with this effect-size limit.
    Wasserstein Empirical transport distance divided by the reference population standard deviation; with zero standard deviation use the unnormalized distance. Compare with wasserstein (0.1).
    KL divergence Compare current and reference numeric-bin probabilities with kl_divergence (0.1).
    Missing schema A declared feature absent from either input records schema_missing; unrelated extra columns are not new declared features.
    Type drift Incompatible feature types record type_drift. Supported numeric/string and boolean representations are normalized where valid; this is not a blanket raw-dtype inequality check.
    Missing fraction Nulls and numeric NaNs are missing. Compare with the reference rate, using the quality rule below.
    Nonfinite fraction Numeric NaN and infinity contribute to the fraction; infinity is a quality issue.

    Distribution drift requires both an effect above its own limit and supported sample-aware statistical evidence. Evidence uses Bonferroni correction across feature tests in one report at significance 0.05; repeated windows are not covered by that correction. not_detected is not proof of equal distributions or adequate test power. Schema/type violations are recorded independently.

    The missing-rate reference value is not a configurable alert threshold. An increase from a zero reference rate is an issue; otherwise an increased rate uses a one-sided Fisher test at 0.01. Missing input rows without usable saved predictions can also be quality issues. Do not interpret a displayed reference missing percentage as an allowed limit.

    Choose the reference population

    The monitor replays original training membership from saved source and split evidence, prepares immutable Spark reference tables, and compares current features from the source snapshots recorded with saved predictions. It does not pick an arbitrary latest table or retrain during measurement. See reference preparation and store reference tables.

    The command

    After changing thresholds, validate and deploy the producer, then run activation/scoring registration to update its enrollment. Run a fresh observation from the generated project root:

    databricks bundle validate --strict -t test --profile YOUR_PROFILE
databricks bundle deploy -t test --profile YOUR_PROFILE
databricks bundle run monitoring -t test --profile YOUR_PROFILE

    Open monitoring_report in the run for the saved feature metrics and notes, then Drift and data quality in the shared dashboard. Dashboard refresh alone does not calculate a new drift report.

    What you should see

    Status Meaning
    healthy Measured drift/quality checks passed; model accuracy is not an acceptance gate.
    drift Distribution or declared feature-schema checks detected drift.
    stale The latest scoring commit (batch) or captured request (online) is older than expected_interval_hours, regardless of the last monitoring run.
    never_observed No observation exists for the current enrollment configuration.
    degraded Quality/measurement issues, no usable predicted outputs, or a nonfinite calculated metric.
    failed Monitoring raised a saved error.
    no_data The selected reference or current population is empty.
    disabled Enrollment explicitly paused.
    unavailable A result exists but the scoring or captured-request time is unavailable.

    Counts represent enrollments, not prediction rows. measurement_status retains the underlying measured verdict when freshness changes. No retraining, performance acceptance thresholds or notifications are enabled by the dashboard.

    Measured status precedence is no_data for an empty reference/current population, then drift for a detected feature change, then degraded for incomplete checks, quality problems or invalid measured metrics, otherwise healthy. A quality issue does not erase measured drift. Health freshness is based on scoring commit or captured request time, not the time monitoring reran.

    Read the drift charts

    The drift/quality page keeps two history tables and separates charts by model/version/context. Each identity shows its latest observation's top ten feature PSI values beside their own limits, plus feature counts with drift or unavailable checks over time. Each feature is counted once within its observation even if multiple checks flag it. The count axis uses whole numbers; compact UTC date/time labels keep the chart readable. Hover to see the full window and calculation timestamp. For example, data from 09:00 to 10:00 appears at 10:00 even if the checks ran at 11:30. Drift and Performance date filters use the same window end as their time charts. Calculation time remains available separately in the details. The matching-identity table shows which contexts the shared filters include. The full model/table inventory remains on Overview.

    KS p-value is not an effect-size threshold. Unavailable checks are shown separately, and missing values never become zero. PSI is only one drift check; the counts and table include other distribution and schema checks too.

    Drift columns show each metric's value / its own limit. KS p-value is diagnostic only; it is never divided by the KS statistic's threshold. Missing features and changed types stay visible. Quality rows identify model version, scoring time and feature, with separate missing/nonfinite percentages. Both tables retain observation history.

    Filters never select an older report; see latest observations and page filters. The PSI bars retain at most ten features per identity before feature filtering; use the history tables for the rest.

    The PSI matrix includes numeric and categorical features. Each cell divides a recorded PSI by its own recorded limit; values above 1 receive a fixed highlight. An absent or nonpositive limit leaves the cell blank. Each identity retains its latest 12 full observations and the 10 features with the largest ratios within that history. Feature and date filters narrow this retained set; they do not retrieve older observations. Observation labels include the year and a sequence number, so separate reports for the same window remain separate cells.

    The missing-value matrix uses the same observation and feature bounds, ranking features by their largest missing fraction. Its reference rate is the reference dataset's missing fraction, not an alert limit. A recorded quality issue can depend on a statistical test or unscored inputs. The tooltip identifies that saved decision. Nonfinite fractions remain available in the quality table.

    Latest PSI bars use the newest saved report for each context, as described in latest observations. The drift context summary exposes the newest report status even when charts are empty. Mature performance-window-only reports stay in policy history; they do not replace the full feature observation, current model health or confusion matrix.

    Common errors and fixes

    What you see What to check
    no_data Confirm the pinned reference and selected current window contain rows. Empty data is not proof of no drift.
    degraded or unavailable checks Read the per-feature evidence and quality notes. Unsupported types, too little statistical evidence, unscored inputs and invalid values must be resolved before treating the population as measured.
    Large PSI but no supported drift Inspect effect and statistical evidence separately; meeting one gate does not establish the other.
    Drift but no training request Opt into on_drift: retrain only after reviewing the shared request guards. Quality/schema problems, incomplete checks or stale/freshness guards can block a request.

    Spark measurement limits

    Spark computes regression and confusion-matrix metrics from full-population aggregates, and probability AUC/AP from exact tied-score counts. Numeric drift uses exact empirical-CDF KS/Wasserstein effects and reference percentile bins; rows are not sampled. Ordered CDF and probability curves use an ordered Spark window over distinct values, which can concentrate work on one executor for high-cardinality features. Removing the local row cap does not remove compute, shuffle or executor-memory requirements.

    Statistical evidence is bounded separately: KS uses the exact lattice calculation when the two population sizes multiply to at most 1,000,000, the Core asymptotic method when either size exceeds 10,000, and explicitly named ks_dkw_union_bound evidence in the remaining range. An inconclusive bound is unavailable rather than evidence of no drift. Small categorical domains (at most 50 distinct non-null reference values) keep their exact-category comparison; Spark accepts at most 1,024 current categories on that path. Larger domains use the grouped comparison below. Classification allows at most 256 saved classes. Temporal/nested feature drift and unsupported cardinalities are explicit failures or unavailable checks. These limits bound summaries and supported algorithms, not observation rows.

    Temporal or nested feature checks and unsupported cardinalities stay explicit; missing values never become a zero drift score. Numeric infinities or invalid numeric conversions can make the distribution comparison unavailable while quality evidence remains visible.

    Categorical features with many values

    ZIP codes, cities and product categories can have more than 50 values without being identifiers. With default settings, pandas/Polars and Spark use the same rules:

    1. Count distinct observed non-null reference values. More than 10,000 categories on either side makes the comparison unavailable. The reference must also have at least two non-null observations per distinct value on average: distinct_count / non_null_count <= 0.5. This heuristic excludes mostly unique identifiers; it does not prove that a column is an identifier.
    2. Keep the 50 most frequent reference categories, breaking equal counts by ascending label. Pool all remaining reference and current values into one additional bucket. Current frequencies never select the retained categories. Spark collects bounded category counts, not raw observations.
    3. Calculate psi_categorical and statistical evidence from the 51 buckets. Existing PSI limits, sparse-count tests and feature-family Bonferroni correction still apply. Evidence test names end in _top50_other to expose the grouping. A drift decision still needs both effect and statistical support.

    The additional new_category_rate is the fraction of non-null current rows whose label never appeared anywhere in the reference, including its pooled tail. For example, 25 rows with unseen ZIP codes among 100 non-null current rows give 0.25, even if another 100 current rows are null. It is diagnostic: monitoring records threshold: null and has_issue: false. It does not independently trigger retraining. The direct Core DriftMetric retains its numeric threshold field with the harmless upper bound 1.0; has_drift is always false for this metric.

    from skyulf.profiling.drift import DriftCalculator
import polars as pl

reference = pl.DataFrame({"zip": [f"zip{i:03}" for i in range(90)] * 20})
current = pl.DataFrame({"zip": ["zip089"] * 75 + ["new_zip"] * 25})
report = DriftCalculator(reference, current).calculate_drift()
column = report.column_drifts["zip"]
print({metric.metric: metric.value for metric in column.metrics})
# Includes new_category_rate: 0.25 and the measured psi_categorical value.
print(column.evidence.model_dump())

    Pooling can conceal redistribution within the tail, even when all tail labels change. Inspect novelty alongside PSI; a small PSI does not establish stable rare-category frequencies. Missingness is measured separately by the monitoring quality checks. Columns with 50 or fewer reference categories retain their existing metrics and evidence; they do not gain new_category_rate.

    Configure thresholds and measurement limits

    Use the existing monitoring_drift_thresholds JSON variable in your producer's deployment/variables.yml or target overrides. Register the changed enrollment through normal activation or scoring before the next monitoring job. These are per-monitor settings; changing the dashboard does not change a measurement.

    Key Default when absent Meaning and valid range
    psi 0.2 PSI effect threshold; finite and positive.
    ks_statistic 0.1 Maximum-CDF-distance effect threshold; finite and positive.
    wasserstein 0.1 Distance normalized by reference standard deviation; finite and positive.
    kl_divergence 0.1 KL effect threshold; finite and positive.
    categorical_top_k 50 Retained reference levels before pooling; integer 1–1,000,000, no larger than max_category_summaries.
    id_like_uniqueness 0.5 Maximum distinct/non-null reference ratio for the grouped path; (0, 1]. Increase only for known categorical domains.
    max_category_summaries 10000 Maximum distinct categories per population on the grouped path; integer 1–1,000,000. An explicit override also caps exact-category comparisons.
    psi_moderate 0.1 Moderate severity wording, separate from the PSI alarm threshold. Positive and below psi_critical.
    psi_critical 0.25 Critical severity wording. Positive and above psi_moderate.
    monitor_max_rows Existing observation budget, capped at 1,000,000 Explicit non-Spark observation row budget; integer 1–1,000,000.
    monitor_max_bytes Existing observation budget, capped at 1 GiB Explicit non-Spark observation byte budget; integer 1–1 GiB.
    missing_markers None Object mapping monitored integer or floating-point feature columns to 1–100 marker values, for example {"co_gt": [-200]}. Matching values count as missing in both the reference and the current population. See missing-value markers. Monitoring only.

    monitor_max_rows and monitor_max_bytes override driver materialization budgets, not feature thresholds. Without them, the producer's budgets remain in effect; direct MonitorConfig defaults remain 10,000 rows and 64 MiB. Overrides stay within the existing 1,000,000-row / 1 GiB safety ceilings. For larger observations use Spark monitoring. Spark validates these keys but does not impose local row/byte budgets on distributed observations. It still bounds category summaries. Very large category limits increase driver memory for count summaries; a large top K also enlarges the statistical test's contingency table and its diagnostic details. Increase them only as needed.

    # Target variable override; JSON numbers must be numbers, not quoted strings.
variables:
  monitoring_drift_thresholds: >-
    {"psi": 0.2, "categorical_top_k": 30,
     "id_like_uniqueness": 0.75, "max_category_summaries": 20000,
     "psi_moderate": 0.15, "psi_critical": 0.3,
     "monitor_max_rows": 200000, "monitor_max_bytes": 268435456}

    The same dictionary, without missing_markers, can be passed to DriftCalculator(...).calculate_drift(...), which rejects that key; row/byte keys are consumed by monitoring enrollment only. Category evidence names reflect the chosen K, for example chi_square_top30_other. Increasing K preserves more rare labels but increases summary work and can make sparse evidence harder to establish. Changing severity bands changes suggestions, not the independent effect/statistical gates. Omitted keys retain historical output and enrollment fields. With no categorical overrides, the small-domain Spark path retains its 1,024-current-category limit.

    These settings do not expose preprocessing probe minimum/sample caps or float tolerances, the PowerTransformer 10% fit guard, SHAP's two-row minimum, Spark's maximum class count or its exact-KS cell limit. Those remain fixed contracts.

    Missing-value markers

    Monitoring measures the raw scoring inputs, before the model's preprocessing. A source that writes a code such as -200 for "no reading" therefore looks like a real measurement: its missing fraction stays 0 and drift includes the code. List such codes per column to count them as missing instead:

    variables:
  monitoring_drift_thresholds: '{"missing_markers": {"co_gt": [-200], "hour": [-1]}}'

    For a sensor that writes -200 during outages:

    Without markers With {"co_gt": [-200]}
    co_gt missing fraction 0, because -200 counts as a reading The share of rows without a reading
    co_gt drift Includes the -200 values, so more outages look like a shift in the readings Compares real readings only
    More outages than in training Not visible A quality issue when the increase is significant
    Model, predictions and training Unchanged Unchanged
    • Markers apply to the reference and the current population before quality and drift, in Spark and in-memory monitoring alike. Stored reference tables keep raw rows, so changing markers takes effect at the next observation.
    • A marker matches exactly in the column's own type. Integer columns need whole numbers within their range. Floating-point columns need a value that type holds exactly: a 32-bit float column accepts -200 or -999.5, but not 0.1. Decimal, text and other columns cannot carry markers.
    • A marker for a column that is not a monitored feature, or that has no exact value in the column's type, fails the observation instead of being skipped.
    • A marked value is then an ordinary missing value. Missingness above the training rate, and a missing value on a row without a saved prediction (an excluded row), are quality issues.
    • Without missing_markers, reports are unchanged.

    Notifications

    Job failures and measured drift are separate events. A successful monitoring run can report drift, missing evidence or performance loss. Configure native job notifications for failed runs in your target variables, and a duration warning as a health rule on the monitoring job of the same target in deployment/targets.yml:

    targets:
  test:
    variables:
      monitoring_email_notifications:
        on_failure: [ml-operations@example.com]
        on_duration_warning_threshold_exceeded: [ml-operations@example.com]
      monitoring_webhook_notifications:
        on_failure:
          - id: YOUR_EXISTING_NOTIFICATION_DESTINATION_ID
    resources:
      jobs:
        monitoring:
          health:
            rules:
              - metric: RUN_DURATION_SECONDS
                op: GREATER_THAN
                value: 1800

    Jobs have no health block by default: an empty rule list fails bundle deploy with the Terraform engine. The warning value must not exceed the job's monitoring_timeout_seconds.

    Replace the example email/destination before deploying. Webhooks use an existing workspace notification destination ID, not a URL. Empty defaults send nothing. To notify on monitoring findings, create a separate SQL alert over the shared store's existing monitoring_issues view. For example:

    SELECT count(DISTINCT monitor_id) AS models_requiring_attention
FROM my_catalog.skyulf_monitoring.monitoring_issues
WHERE environment = 'prod';

    Alert when models_requiring_attention > 0; choose an existing warehouse, notification destination and a schedule aligned with the monitoring job. This view includes drift, quality, policy loss and missing/stale evidence, with current enrollment and configuration filtering. Multiple feature issues for one monitor count once. Open the view or dashboard for the individual reasons. Narrow project or model_name to alert on a particular workload. The Bundle does not create this SQL alert or any recipient automatically.
