## v0.7.9

### 🔧 Backend

- **New `GET /api/config` endpoint** (`backend/config/routes.py`): exposes
  `max_upload_size_bytes` and `allowed_extensions` from the backend `Settings`
  (`MAX_UPLOAD_SIZE` / `ALLOWED_EXTENSIONS`), so the frontend no longer
  hardcodes upload limits that can drift from server configuration.

### 🎨 Frontend

- **`FileUpload` node now reads upload limits from the backend**: new
  `useUploadConfig` hook (React Query, 5-minute stale) feeds the size check,
  the "file too large" error text, the `accept` attribute, and the
  "Supports …" caption in `FileUpload.tsx`. No hardcoded fallbacks remain —
  until the config loads, the client skips the size/extension pre-checks and
  the server enforces the real limits.

### 🐛 Bug Fixes

- **Frontend — upload limits:** `FileUpload` previously hardcoded a 10 GB
  size cap and an `accept` list that could silently diverge from the
  backend's `MAX_UPLOAD_SIZE` / `ALLOWED_EXTENSIONS`; both are now driven by
  `GET /api/config`.

- **Frontend — Experiments page:** Extracted the evaluation fetch +
  threshold-tuning state from `ExperimentsPage.tsx` into the unit-testable
  `useEvaluationFetch` hook
  (`frontend/ml-canvas/src/components/pages/ExperimentsPage/hooks/useEvaluationFetch.ts`)
  with a monotonic request-sequence guard, so a late/stale evaluation response
  can no longer clobber a newer job's data in the evaluation panel (audit
  finding F-33).
- **Backend — Threshold tuning:** `roc_auc` threshold tuning no longer
  500s on string class labels (e.g. `yes`/`no` targets). Metric scorers are
  now built per request via `_build_scorer()`
  (`backend/ml_pipeline/_services/threshold_tuning_service.py`); the `roc_auc`
  scorer maps raw labels to 0/1 positive-indicator arrays before
  `roc_auc_score`, so string targets work while numeric 0/1 behavior is
  unchanged (rank-preserving). (Audit finding F-34.)
- **Backend — Threshold tuning:** `f1`/`precision`/`recall` threshold
  tuning on binary jobs now scores the **positive class**
  (`average="binary"`, `pos_label=classes[1]`) instead of a weighted
  class mixture. Weighted recall is mathematically identical to accuracy,
  so tuning "Recall" was actually tuning accuracy and could make
  positive-class recall *worse* than the un-tuned model (audit finding
  F-35). Multiclass behavior is unchanged.
- **Core — Explainability:** SHAP explainability restored for the six
  non-callable classifier families (SVC-RBF, KNN, GaussianNB, MLP, Voting,
  Stacking) that raised `TypeError` in `shap.Explainer`. `_build_explainer`
  (`skyulf-core/skyulf/modeling/_explainability/shap_explanation.py`) now
  falls back to the estimator's `predict_proba` (or `predict`) as the
  predictor; 3 new unit tests (25/25 pass). The Experiments page
  artifact-coverage reason now says *not supported for this model type*
  instead of blaming an older run. Permutation feature importance for these
  families remains unsupported (`None`) — follow-up. (Audit finding F-37.)
- **Frontend — Pipeline templates:** Moved `TrainTestSplitter` upstream of
  impute/encode/scale in the four canvas templates
  (`frontend/ml-canvas/src/core/templates/pipelineTemplates.ts`:
  `TABULAR_CLASSIFICATION`, `TABULAR_REGRESSION`, `TEXT_CLASSIFICATION`,
  `ENSEMBLE_CLASSIFICATION`). Previously the templates fit data-dependent
  steps (imputer, encoder, scaler) on the full dataset *before* splitting,
  leaking test-set statistics into training; the split now runs first so
  those steps fit on the training partition only (audit finding A2.2).
- **Frontend — Upload:** The client-side upload limit in
  `frontend/ml-canvas/src/modules/nodes/data/FileUpload.tsx` was hardcoded
  to 500 MB while the server allows 10 GB
  (`backend/config/mixins/files.py`), and the file picker's `accept` list
  hid `.xls`/`.txt`/`.feather` although the server accepts them. The client
  limit is now 10 GB (error message shows GB) and `accept` matches the
  server's `ALLOWED_EXTENSIONS` (audit finding A2.6).

## v0.7.8

### 🐛 Bug Fixes
- `LabelEncoder` and `OrdinalEncoder` could silently map every known feature/target value to `missing_code`/`unknown_value` when a Polars-backed fit batch and apply batch had different null presence. Polars' native `.to_numpy()` casts integer columns/series containing nulls to float (NaN), which flips the string representation of every value (e.g. `"1"` becomes `"1.0"`) depending on whether nulls happen to be present in that particular batch. Fit paths converted target/feature columns via `.to_numpy().astype(str)` directly, while apply paths already cast to `Utf8` and `fill_null("nan")` first — so fit and apply could learn/produce mismatched string categories. Both fit paths now perform the same `Utf8` cast + `fill_null("nan")` in Polars *before* calling `.to_numpy()`, matching the existing apply-time representation (`skyulf-core/skyulf/preprocessing/encoding/label.py`, `skyulf-core/skyulf/preprocessing/encoding/ordinal.py`).

- `WOEEncoder` fit could learn WOE mapping keys for integer categorical columns that didn't match what the Polars apply path would render for the same values, causing every known category to silently fall back to the encoder's `default` value. `_woe_fit` always converted the input to pandas before stringifying columns (`frame[col].astype(str)`); pandas upcasts an integer column containing nulls to float, so `1` became the key `"1.0"`, while the Polars apply path (`_woe_apply_polars`) casts natively to `Utf8` and renders `"1"`. Fit now casts Polars integer/categorical columns to `Utf8` with `fill_null("nan")` natively *before* the pandas conversion, so the string keys match the Polars apply-time representation exactly; the pandas-only fit/apply path is unaffected (`skyulf-core/skyulf/preprocessing/encoding/woe.py`).
- Addressed code review follow-ups on the `LabelEncoder`/`OrdinalEncoder` null-handling fix above: replaced a `hasattr(y, "fill_null")` duck-typing check with an explicit `isinstance(y, pl.Series)` to avoid misrouting non-Polars objects, and clarified docstrings on the differing 1-D vs. 2-D return shapes for sklearn's `LabelEncoder` vs. `OrdinalEncoder`.
- Clustering nodes (K-Means, Mini-Batch K-Means, Gaussian Mixture, Birch) silently let non-numeric columns reach sklearn's distance calculations under the Polars engine: `_select_numeric_features` in `modeling/clustering.py` only checked `isinstance(X, pd.DataFrame)`, so a raw `pl.DataFrame`/`SkyulfPolarsWrapper` — the form `extract_xy` returns when no target column is configured, the normal clustering case — skipped the numeric-only filter entirely. The same function now filters Polars input natively using the `POLARS_NUMERIC_BOOL_DTYPES` set already used for this purpose in `modeling/_evaluation/clustering.py`.
- `_drop_reference_column` in the same module always called `X.drop(columns=[reference_column])`, which raises `TypeError` on any real Polars DataFrame — Polars' `.drop()` takes column names positionally and has no `columns=` keyword, unlike pandas. Any clustering node configured with a "reference column" (e.g. a known label kept alongside the clustering output for evaluation) crashed outright under the Polars engine. Now branches on the pandas-vs-Polars calling convention, mirroring the existing correct pattern in `modeling/base.py::_drop_target_column`.
- Time-series `LagFeatures` and `RollingAggregate` nodes produced materially different values between engines for rows whose `group_by` key was null: pandas' `DataFrame.groupby(...)` defaults to `dropna=True`, excluding null-key rows from any group entirely (so their lag/rolling values are unrelated to their actual prior null-group history), while the Polars path's `.over(group_by)` has always treated null as a normal, self-consistent group key. Both `_pandas_lag_column` (`preprocessing/time_series/lag.py`) and `_pandas_roll_column` (`preprocessing/time_series/rolling.py`) now pass `dropna=False` explicitly, so a null `group_by` key behaves identically to the Polars engine on the same input.

### 🧹 Cleanup
- Removed unreachable Polars↔NumPy conversion fallbacks that could never execute. `PandasEngine.to_numpy` and `PolarsEngine.to_numpy` each carried a dead `isinstance(..., SkyulfPandasWrapper/SkyulfPolarsWrapper)` branch that duplicated the preceding `hasattr(df, "to_numpy")` check, since both wrapper classes delegate to their wrapped DataFrame via `__getattr__` and therefore always report `to_numpy` present. `_y_to_numpy` in `preprocessing/encoding/target.py` carried a `.to_pandas().to_numpy()` fallback for objects lacking `.to_numpy()`, which is unreachable for any real pandas or Polars Series/DataFrame passed through this codebase's engines — both have exposed `.to_numpy()` natively for years. No behavior change; simplifies `skyulf-core/skyulf/engines/pandas_engine.py`, `skyulf-core/skyulf/engines/polars_engine.py`, and `skyulf-core/skyulf/preprocessing/encoding/target.py`.

### 🐛 Bug Fixes (deep re-audit round)

A follow-up audit dispatched 6 parallel subagents (research + rubber-duck + high-reasoning models) across both `backend/` (previously unaudited) and a second, skeptical re-audit of `skyulf-core/`, empirically re-verifying every finding before fixing it.

- **[Severe]** `DummyEncoder` could silently zero out every dummy-indicator column for every row on a train/apply engine or null-presence mismatch. Its pandas fit/apply paths (`_dummy_fit_pandas`/`_dummy_apply_pandas`) called `.astype(str)` directly on a column that pandas silently upcasts to `float64` whenever nulls are present, so `1` became the key `"1.0"` at apply time while fit-time (no nulls) recorded categories as `"1"`, `"2"`, `"3"` — every row's category lookup then missed and the encoded output was 100% zeros with no error raised. Added a `_pandas_col_to_str()` helper that casts integer-valued float columns to nullable `Int64` before stringifying (avoiding the spurious `.0` suffix) and preserves nulls as real NaN rather than the literal string `"<NA>"`/`"nan"` (`skyulf-core/skyulf/preprocessing/encoding/dummy.py`).
- A rubber-duck review of the `clustering.py::_select_numeric_features` fix (above, in the previous v0.7.8 entry) found the fix itself introduced a regression: its `hasattr(X, "dtypes") and hasattr(X, "columns")` duck-typing check also matched this codebase's own `SkyulfPandasWrapper` (which delegates both attributes via `__getattr__`), misrouting it into the Polars-specific numeric-dtype-filtering branch and silently dropping every column, including numeric ones — worse than the original bug for that object type. Replaced with an explicit `isinstance(X, pl.DataFrame | SkyulfPolarsWrapper)` check (`skyulf-core/skyulf/modeling/clustering.py`).
- `StatefulEstimator.fit_predict` (`modeling/base.py`) and `StatefulTransformer.transform` (`preprocessing/base.py`) each only checked `isinstance(dataset, pd.DataFrame)` before falling through to tuple/`SplitDataset`-shaped branches, so a raw (unwrapped) `pl.DataFrame` — reachable via `pipeline.py`'s no-splitter fallback path, and via direct public-API use of `StatefulTransformer.transform` — crashed with `AttributeError: 'DataFrame' object has no attribute 'train'`. Both now detect any frame-like object (pandas, raw Polars, or wrapper) via `hasattr(dataset, "shape") and hasattr(dataset, "columns")` before the tuple/split branches, building an engine-matching empty "test" placeholder instead of always defaulting to `pd.DataFrame()`.
- `_compute_reference_crosstab_polars` (`modeling/_evaluation/clustering.py`) produced a different reference crosstab than the pandas path whenever the reference column had a null value: pandas' `pd.crosstab` silently drops NaN rows from the reference column by default, while the Polars path's `group_by` treated null as a legitimate group, adding a bogus `"None"` category not present in the pandas output. Now filters `pl.col(ref_name).is_not_null()` before grouping, matching pandas' behavior exactly.
- `_calculate_eta_for_column` (`profiling/_analyzer/target.py`) let a null target-column value form a phantom group in the correlation-ratio (η) calculation, letting an unrelated group of null-target rows distort the statistic. Now filters null targets out before `.group_by(target_col)`.
- `_compute_seasonality` (`profiling/_analyzer/temporal.py`) produced a bogus `{"day": None, ...}` / `{"month": None, ...}` bucket for rows with a null date. Both the day-of-week and month-of-year aggregation pipelines now filter out null dates first.
- `_analyze_categorical` (`profiling/_analyzer/categorical.py`) rendered a null value in Polars' `value_counts()` top-k output as the literal string `"None"`, indistinguishable from a genuine category of that name. Null entries are now skipped entirely rather than stringified.
- `_pca_points`/`_cluster_pca_points` (`profiling/_analyzer/multivariate.py`) had the same `str(None)` display bug as above for per-row PCA/cluster point labels — a null label rendered as the string `"None"` instead of staying `None` (JSON `null`). Both now null-check the specific row's label value before stringifying, rather than only checking truthiness of the whole labels collection.
- `backend/data_ingestion/engine/profiler.py::DataProfiler.profile` had an incomplete numeric-dtype allow-list (`Int64`/`Float64`/`Int32`/`Float32` only), so a `pl.UInt8`/`Int8`/`Int16`/`UInt16`/`UInt32`/`UInt64` column silently fell through both the numeric and string branches and received zero statistics. The allow-list now covers every integer/float dtype variant.
- `backend/ml_pipeline/_internal/_advisor.py::DataProfiler.generate_profile` crashed with `TypeError: float() argument must be a string or a real number, not 'NAType'` on any all-null pandas nullable-dtype column (`Int64`/`boolean`, produced by this codebase's own Casting node), since `.min()`/`.max()`/`.mean()`/`.std()`/`.skew()` on such columns return the `pd.NA` sentinel rather than `NaN`. Added a `_safe_float()` helper that returns `None` for `pd.NA`/`NaN` instead of raising, so one bad column degrades gracefully instead of aborting the whole profile.
- `backend/ml_pipeline/_internal/_routers/preview.py::_to_records` round-tripped every Polars preview frame through `.to_pandas()` with default settings, which upcasts an Int*/Boolean column containing nulls to numpy `float64`/`object` (there's no native nullable-int/bool numpy dtype) — silently rendering an integer `5` as `5.0` and a boolean as an ambiguous object in the JSON preview payload sent to the frontend. Now uses Polars' own `.to_dicts()`, preserving exact int/bool/None values and removing a redundant intermediate conversion. `_to_pandas_safe` (feeding the advisor's numeric/categorical classification) now passes `use_pyarrow_extension_array=True` to `.to_pandas()` to keep nullable dtypes intact for downstream `is_numeric_dtype()`/`is_bool_dtype()` checks.

### 🧹 Cleanup / Findings Reviewed, Not Changed
- Confirmed **not** a bug: `count_vectorizer.py`/`tfidf_vectorizer.py`'s null-presence-driven `.0`-suffix string difference is masked by sklearn's default tokenizer dropping the single-character `.0` token, so vocabularies are identical across engines regardless. `tokenizer.py`/`sentence_embedder.py` are stateless (no learned dict lookup), so any representation difference is cosmetic, not a correctness bug.
- Confirmed **not reachable in production**: `_tuning/engine.py::_is_multiclass_target`'s non-numpy-`y` handling gap (only the internal `fit()` caller feeds it, and that path always pre-converts to numpy); `_explainability/shap_explanation.py::compute_shap_explanation`'s pandas-only `X.empty` check (the only production caller in `backend/`'s pipeline engine always produces a pandas frame).
- Backend architecture note: `backend/`'s `PipelineEngine` (execution engine backing job runs) is pandas-only by design — its `DataCatalog` implementations always return `pd.DataFrame`, so Polars never reaches the execution engine's `isinstance(x, pd.DataFrame)` checks in practice; those are correct-as-designed, not dead code. Polars only flows through `backend/`'s ingestion/EDA/monitoring utilities, which are architecturally separate.
- Lower-severity backend findings identified but deferred (latent/low-confidence/dead-code-only, not fixed this round): `data_ingestion/serialization.py`'s Polars-path JSON-safety gap (module appears unreferenced in production); `_advisor.py`'s datetime-as-categorical misclassification; dead `query` param on `LocalFileConnector`/`S3Connector.fetch_data`; a redundant CSV-schema retry in `S3Connector.get_schema`; dead-code-shaped pandas fallback branches in `eda/router.py::_load_decomposition_dataframe` and `monitoring/router.py::_load_reference_dataframe`; misleading identical-branch dead code in `deployment/service.py::_maybe_decode_predictions`; the entirely-dead `"tune"` renderer family in `_execution/summary.py`; a latent (no live call site) aliasing risk in `_execution/engine/_merge.py::_merge_frames` returning by reference.

### 🐛 Bug Fixes
- Installing `shap` was not enough: SHAP explanations still came back empty for every tree model. `compute_shap_explanation` always built `shap.Explainer(model, masker)` with an explicit `Independent` background masker, which forces tree ensembles into SHAP's *interventional* perturbation mode — a documented source of `ExplainerError: Additivity check failed` on this `shap` 0.52 / scikit-learn 1.8 pairing. The bare `except Exception: logger.debug(...)` then swallowed it silently for every job, so no run in the database ever carried a `shap_explanation`. Tree models now use `TreeExplainer(..., feature_perturbation="tree_path_dependent")`, which computes exact Shapley values from the tree structure and needs no background data; non-tree models keep the masker path, and the outer failure is logged at `warning` with the exception instead of being hidden (`skyulf-core/skyulf/modeling/_explainability/shap_explanation.py`).
- The same call also silently re-subsampled its input: `shap.Explainer(model, sample)` builds a default masker with its own `max_samples=100`, so asking for 200 samples quietly produced 100. The masker is now constructed explicitly at the size of the sample passed in.

## v0.7.6

Closes the last 9 open findings from the `2026-08-07` audit rerun (`CAN-003`, `DAT-007`, `EXP-003`, `EXP-007`,
`OPS-001`–`OPS-005`).

### 🔧 Backend
- `GET /monitoring/errors` and `GET /monitoring/pipeline-logs` now filter server-side across the full table and return `facets` plus `total_unfiltered`, mirroring the Audit Log contract added in v0.7.5. Errors are classified into a `severity` (5xx → critical, 4xx → warning, else info) so the client can facet on it instead of substring-matching a page it already downloaded (`backend/monitoring/router.py`, OPS-004).
- Slow-node aggregates carry their own provenance: `SlowNodesResponse` states its `unit`, and each `SlowNodeAggregate` reports `is_single_run`, `sample_is_representative`, and up to five `contributing_runs` with job/pipeline/node/dataset identity, with runs beyond 1.5× the average flagged as outliers. Previously the route returned a bare average with no way to tell one slow run from a systemic cost (`backend/monitoring/router.py`, OPS-005).
- Drift checks became durable alerts. `DriftCheckResult` gained severity, disposition status/owner/timestamps, a `disposition_history` audit trail, `deployment_id`/`model_version` links, and **pinned** threshold columns backed by a new immutable `DriftThresholdVersion` table — so changing a threshold no longer silently re-scores the history of past alerts. A row is now persisted for every outcome (`completed`, `no_baseline`, `failed`) rather than only successful evaluations, and `GET /drift/alerts/{id}` plus `PATCH /drift/alerts/{id}/disposition` expose the acknowledge → resolve/reopen state machine (409 on an invalid transition). Also fixed evidence being stored double-nested under `column_drifts` instead of the flat per-column shape the client expects (`backend/monitoring/router.py`, `backend/database/models.py`, OPS-003).
- `POST /jobs/{job_id}/retry` resubmits a terminal job from its stored graph, so a failed run can be recovered from the Jobs table instead of being rebuilt by hand on the Canvas (`backend/ml_pipeline/_internal/_routers/jobs.py`, OPS-001).
- Deployments record `previous_deployment_id`, and both `/history` and the details route enrich every row (not just the active one) with `dataset_id` and `version` resolved from the source `TrainingJob` — the missing links that made a replaced deployment untraceable (`backend/ml_pipeline/deployment/`, OPS-002).

### 🎨 Frontend
- Canvas recovery names its sources. `loadCanvasSnapshotDiagnostic()` distinguishes `available` / `empty` / `corrupt` / `version-mismatch` / `storage-error` instead of collapsing all four failures into a silent `null`, so a snapshot that cannot be used now says so in a dismissible non-blocking message rather than looking like "nothing was ever saved". The restore prompt is labelled `Autosave`, re-probes whenever the canvas becomes empty instead of only once on mount, and the Toolbar's overwrite confirmations name their source kind (`Server version` / `Local recent`). A successful restore fits and focuses the recovered graph (CAN-003).
- EDA charts no longer rely on color or a hover tooltip to carry meaning.
