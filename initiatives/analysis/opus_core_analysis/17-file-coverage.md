## Findings

<a id="oc-140"></a>
### OC-140 🟠 High — `InvalidValueReplacement` diverges across engines on non-numeric columns

**File:** `skyulf/preprocessing/cleaning/invalid_value.py`

The pandas path calls `pd.to_numeric(df_out[col], errors="coerce")` before
applying the rule (line ~155). The polars path has **no equivalent coercion** —
it builds `pl.when(expr < 0)` directly against the raw column.

When a user explicitly selects a string-typed column (common when a CSV column
contains a stray `"N/A"`), the two engines do entirely different things:

| case | pandas | polars |
|---|---|---|
| numeric column *(control)* | `[5.0, -999.0, 2.0, 7.0]` | `[5.0, -999.0, 2.0, 7.0]` — **MATCH** |
| string column + `rule="negative"` | `[5.0, -999.0, nan, 7.0]` — silent data loss | `ComputeError: cannot compare string with numeric type` — hard fail |

Reproduction (control included to prove the probe is valid):

```python
from skyulf.preprocessing.cleaning.invalid_value import (
    InvalidValueReplacementCalculator as C, InvalidValueReplacementApplier as A)
cfg = {"columns": ["a"], "rule": "negative", "replacement": -999.0}
df  = pd.DataFrame({"a": ["5", "-3", "abc", "7"]})   # or pl.DataFrame(...)
A().apply(df, C().fit(df, cfg))
```

Both behaviours are defensible in isolation; being *inconsistent* violates the
library's core dual-engine contract. Worse, the pandas branch destroys `"abc"`
silently. Suggested fix: decide one policy — either coerce in both engines
(`pl.col(c).cast(pl.Float64, strict=False)`) or validate dtype at fit time and
raise in both.

<a id="oc-142"></a>
### OC-142 🟠 High — correlation ratio η can exceed 1.0, inverting EDA rankings

**File:** `skyulf/profiling/_analyzer/target.py` — `_calculate_eta_for_column`

η (correlation ratio) is mathematically bounded to `[0, 1]`. This
implementation can return values well above 1 because SS_between and SS_total
are computed over **different row sets**:

```python
ss_total = self.df.select(((pl.col(col) - global_mean) ** 2).sum()).item()   # nulls excluded
groups   = ... .agg([pl.len().alias("n"), pl.col(col).mean().alias("mean")]) # pl.len() COUNTS nulls
ss_between += n * ((mean_group - global_mean) ** 2)                          # inflated by null rows
```

`pl.len()` counts every row in the group, including rows where `col` is null,
while `mean()` ignores them. Each null therefore adds a full `(mean - global_mean)²`
term to the numerator that contributed nothing to the denominator.

Measured:

| input | η | valid? |
|---|---|---|
| no nulls *(control)* | `0.9839` | ✅ within `[0, 1]` |
| group `b` mostly null | **`2.6454`** | ❌ impossible |

This is not merely cosmetic. `_calculate_categorical_target_associations`
returns `dict(sorted(..., reverse=True))` — results are **ranked by η**. A
column that is 90% null is inflated the most, so the *emptiest* column is
presented to the user as the *most strongly associated* feature.

Fix: count only non-null values per group, e.g.
`pl.col(col).drop_nulls().len().alias("n")`, and compute `global_mean`/`ss_total`
over the same target-non-null subset used for the groups. Optionally clamp to
`min(1.0, ...)` as defence in depth.

<a id="oc-143"></a>
### OC-143 🟠 High — RFE silently ignores the number of features the user asked for

**Files:** `skyulf/preprocessing/feature_selection/_common.py:239`,
`frontend/ml-canvas/src/modules/nodes/processing/FeatureSelectionNode.tsx:405`

The RFE panel's only feature-count input is labelled **"K (Number of Features)"**
and writes `config.k`. `pipelineConverter` passes `node.data` through unchanged.
But the backend reads a different key:

```python
n_features_to_select=config.get("n_features_to_select"),   # never present
```

`n_features_to_select` appears in **exactly one place in the entire repository** —
that read. Nothing ever writes it. So it is always `None`, and sklearn falls back
to its default of selecting **half** the features.

Three-way proof:

| run | requested | selected |
|---|---|---|
| `select_k_best`, `k=3` *(control)* | 3 | **3** ✅ probe valid |
| `rfe`, `k=3` *(what the UI sends)* | 3 | **5** ❌ |
| `rfe`, `n_features_to_select=3` *(proof of cause)* | 3 | **3** ✅ |

The user sets K=3, gets 5, and there is no error or warning. Note `step` — the
other RFE field — *does* match (`config.get("step", 1)`), which is why this
slipped through: the panel looks wired up.

Fix: read `config.get("n_features_to_select", config.get("k"))`, mirroring the
alias tolerance `_normalize_univariate_method` already provides for method names.

**Why the test suite never caught this** (established later, by auditing the
fixture file `tests/test_cases/preprocessing/feature_selection_common.json`):
the fixtures test the two selectors with **different parameter names** —

```text
build_univariate_selector:
  select_k_best:   { k: 3,                      attr_name: k }
build_model_selector:
  rfe:             { n_features_to_select: 2,   attr_name: n_features_to_select }
```

`select_k_best` is exercised with `k`, but `rfe` is exercised only with
`n_features_to_select` — the *internal* name that already works. The `k` path
for RFE, which is the one the UI actually sends, has **no test at all**. The
fixture encodes the bug as if it were the intended contract, which is why a
green suite coexisted with a broken feature.

Add a regression case asserting `rfe` + `k=3` selects exactly 3 features.

<a id="oc-144"></a>
### OC-144 ⚪ Low — distance column is named `_km` even when the unit is miles

**File:** `skyulf/preprocessing/geo/distance.py`

`unit` accepts `"km"` or `"mi"` and correctly rescales the Earth radius, but
`output_column` defaults to the hard-coded `"geo_distance_km"` in three places
(`node_meta`, `fit`, and both apply paths). Selecting miles produces a column
named `geo_distance_km` containing miles — mislabelled data flowing downstream
into models and exports. Fix: default to `f"geo_distance_{unit}"`.

## Checked this pass and found sound

Recording negatives explicitly so future passes don't re-investigate:

- **`preprocessing/cleaning/invalid_value.py` — UI alias handling.** The
  `zero_to_nan` / `percentage_bounds` / `age_bounds` no-op bug described in the
  repo instructions **is already fixed** via `_RULE_ALIASES` and
  `_RULE_DEFAULT_BOUNDS`, normalised once at fit time. Verified present.
- **`preprocessing/feature_selection/_common.py` — method-name casing.**
  `_build_model_selector` compares `method == "select_from_model"` with no
  normalisation (unlike `_build_univariate_selector`). This is a *latent*
  fragility only: the frontend emits snake_case (`select_from_model`, `rfe`),
  so it is not currently reachable. Not filed as a bug.
- **`preprocessing/encoding/target.py`.** Target encoding is the classic leakage
  trap; this implementation handles it properly — `fit_transform_train` does
  genuine cross-fitting, and `_resolve_target_encoder_training_cv` guards fold
  counts against small/imbalanced classes with clear errors. No leak found.
- **`modeling/clustering.py`.** The `isinstance` check in `_select_numeric_features`
  is deliberate and correct — a duck-typed `hasattr` check would misroute
  `SkyulfPandasWrapper` (which proxies `.dtypes`/`.columns`) into the polars
  branch and drop every column. Reference column handling is also correct,
  including polars' `*args` drop signature.

## Method

Coverage was computed mechanically, not estimated:

1. Enumerate every `.py` under `skyulf-core/skyulf/` (excluding `build/`,
   `__pycache__/`) → 188 files.
2. Concatenate the full text of `opus_core_analysis.md` + all 18 reports in this
   folder.
3. For each file, test for its full path, then for a *distinctive* basename —
   ambiguous stems (`base`, `utils`, `types`, `config`, `__init__`) are excluded
   from basename matching so that e.g. a mention of some other `base.py` cannot
   falsely mark `modeling/base.py` as covered.
4. Classify the remainder into re-export shims, behaviour-only coverage, and the
   true gap.

The conservative bias is deliberate: a file is only counted as covered when the
evidence is unambiguous.
