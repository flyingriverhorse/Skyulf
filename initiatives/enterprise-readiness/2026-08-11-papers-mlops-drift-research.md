# Papers & Research: Drift Detection, Monitoring, Data Quality, Reproducibility for Skyulf

**Date:** 2026-08-11

**Grounding note:** Before researching, I read skyulf-core's current implementation to calibrate what's already done vs. what's a genuine gap:
- `skyulf-core/skyulf/profiling/drift.py` — a `DriftCalculator` class already computes **PSI, KS-test, Wasserstein distance, and KL-divergence** per-column (numeric via percentile binning; categorical via category-frequency PSI), with configurable thresholds and human-readable suggestions (`skyulf-core/skyulf/profiling/drift.py:48-494`). This is already fairly complete for **univariate, label-free covariate drift** — more complete than many teams build in-house.
- `skyulf-core/skyulf/profiling/expect.py` — lightweight `expect_no_nulls`, `expect_value_range`, `expect_unique`, `expect_columns_exist` (Great-Expectations-style but dependency-free) exist already (`skyulf-core/skyulf/profiling/expect.py:25-31`).
- `skyulf-core/skyulf/core/artifacts.py` — every preprocessing step returns a `TypedDict` artifact (e.g. `StandardScalerArtifact`, `SimpleImputerArtifact` with `missing_counts`/`total_missing`, `IQRArtifact` with `bounds`) — these are fit-time statistics already captured per column, just not yet consumed by a drift/quality subsystem in a first-class way.

Given this baseline, the interesting research gaps are **not** "how do I compute PSI" (already done) but: (1) multivariate/joint drift beyond per-column tests, (2) label-free early-warning signals for silent degradation, (3) which additional data-quality checks are highest-value beyond range/null checks, (4) what actually breaks reproducibility beyond artifact format, and (5) audit/explainability needs specific to regulated industries.

## 1. Data drift / concept drift detection — beyond per-column PSI/KS

**What skyulf already has:** per-column PSI, KS, Wasserstein, KL-divergence (`skyulf-core/skyulf/profiling/drift.py`). This covers **univariate covariate drift** well.

**Gap: multivariate/joint drift.** Per-column tests miss drift in the *joint* distribution (e.g., correlation structure between features shifting even if marginals look stable) — a classic false-negative mode for PSI-style monitoring.

- **"Failing Loudly: An Empirical Study of Methods for Detecting Dataset Shift"** — Rabanser, Günnemann, Lipton, NeurIPS 2018 / arXiv:1810.11953 (485 citations per Semantic Scholar). Empirically compares dataset-shift detectors and finds that a **two-sample test on a dimensionality-reduced representation** (e.g., PCA components, or a pre-trained classifier's softmax output, then MMD or KS on the reduced space) outperforms naive per-feature univariate tests for detecting joint/label shift, especially at low affected-fraction and subtle shift magnitudes. They also propose methods to (a) detect shift, (b) **identify the exemplars that most typify the shift** (which samples are most "foreign"), and (c) **quantify shift malignancy** (does the shift actually hurt downstream accuracy, vs. benign covariate shift).
  - **Differentiation vs. Evidently/WhyLogs:** Evidently does have a "dataset drift" aggregate flag, but doesn't typically surface "these N rows are the ones driving the drift" as first-class UX. Surfacing **typifying exemplars** tied back through skyulf-core's per-step JSON artifacts (which already track e.g. `bounds`, `fill_values`, `missing_counts`) would let a UI say "these 12 rows look like the June-2025 batch, differing mainly in features X, Y" — actionable rather than a single aggregate score.
  - **Integration with skyulf-core JSON artifacts:** A cheap, low-effort version: take the **already-fitted scaler/PCA-like artifacts** (skyulf has `PolynomialFeaturesArtifact`, scaling artifacts with `mean`/`scale`) and reduce dimensionality using existing fit-time stats rather than fitting new PCA — reuse what's already captured instead of retraining a shift detector from scratch. Store the "typifying exemplars" as row indices/hashes in a new `MultivariateDriftArtifact`.
  - **Effort:** M (needs an MMD or 2-sample classifier-based test; scipy alone isn't quite enough — likely wraps a lightweight implementation, not a new heavy dependency).
  - **Library reference:** `alibi-detect` (Seldon) implements MMD-based, classifier-based, and KS-based multivariate drift detectors and is maintained — good reference/wrap candidate rather than reimplementing MMD from scratch. https://github.com/SeldonIO/alibi-detect

- **Population Stability Index / KS / KL-divergence themselves** — classic, and already implemented by skyulf. No new paper needed here; but worth noting the **known weaknesses documented in literature**: PSI is sensitive to binning strategy (skyulf uses percentile-based binning from the reference set — a documented mitigation, see `_calculate_psi` in `skyulf-core/skyulf/profiling/drift.py:411-457`, which already correctly clips out-of-range values rather than silently dropping them — this is actually a subtle correctness fix that many open-source PSI implementations get wrong). This is a **strength worth documenting/marketing**, not a gap.

**Verdict:** Nothing to "re-invent" for univariate drift — skyulf's current implementation is already solid and arguably more careful (out-of-range clipping) than naive reference implementations. The genuine opportunity is **multivariate joint-drift + shift-malignancy classification + typifying exemplars**, informed by Rabanser et al. (2018).

## 2. Model monitoring — early-warning signals for silent degradation

**Core question:** what predicts silent degradation *before* ground-truth accuracy is available (labels are almost always delayed/absent in production)?

- **"Monitoring and Explainability of Models in Production"** — Klaise, Van Looveren, Cobb, Scillitoe, Samoili, Athanasopoulos, MLOps workshop @ ICML 2020 / arXiv:2007.06299 (Seldon team). Argues the three pillars of production monitoring absent ground truth are: **(1) outlier detection** (is this individual input/prediction anomalous relative to training distribution — a per-instance signal, distinct from aggregate drift), **(2) drift detection** (population-level, aggregate — what skyulf's `DriftCalculator` already does), and **(3) adversarial/actionability detection**. Crucially, they argue **prediction-distribution monitoring is a cheap, always-available proxy signal**: monitoring the distribution of model *outputs* (predicted class probabilities / predicted values) is far cheaper than monitoring all input features jointly, and output-distribution shift is often the **first symptom** visible before input drift is even detectable per-feature, because models can amplify small input shifts into larger output shifts (especially near decision boundaries).
  - **Concrete translation for skyulf:** skyulf's `DriftCalculator` currently drifts *input features*. A very cheap addition: apply the **exact same `DriftCalculator.calculate_drift()` machinery** to the **model's prediction column** (predicted probability for classification, predicted value for regression) between a reference prediction batch and current — this requires **zero new code**, just calling the existing drift calculator on `y_pred` instead of `X`. This is the single cheapest, highest-leverage addition identified in this whole research round.
  - **Effort:** S (reuses 100% of existing `DriftCalculator` code — just needs a wrapper that stores reference-time prediction distributions in the model registry artifact and re-invokes drift calc against a rolling window of production predictions).
  - **Differentiation vs. MLflow/Evidently:** Evidently does have "prediction drift" as a preset, so this specific idea alone isn't fully differentiated — but wiring it natively into skyulf-core's fit-time JSON artifact (so the reference prediction distribution is captured **at model-registration time**, not as a bolted-on separate monitoring step) is a structural integration advantage: it becomes part of the same versioned JSON that already describes the pipeline, rather than a separate monitoring config.

- **Outlier/novelty detection as a complementary per-instance signal** (also from Klaise et al., arXiv:2007.06299): per-instance outlier scores (e.g., isolation-forest or reconstruction-error based) catch anomalous individual predictions that aggregate drift tests smooth over (a small number of very wrong/weird inputs won't move a KS-test but may be operationally important — e.g., fraud edge case, malformed record). Skyulf already has an `EllipticEnvelopeArtifact` for outlier detection in preprocessing (`skyulf-core/skyulf/core/artifacts.py:113-118`) — the fit-time contamination/model params are already captured; the gap is **applying the already-fitted outlier model at inference/monitoring time** to flag individual production rows, not just at training-time cleaning.
  - **Effort:** S–M (the fitted `EllipticEnvelope` object already exists in the artifact; needs a monitoring-time "apply" path plus a per-row anomaly-score aggregation).

**Verdict:** The single most actionable/cheapest finding in this whole report is **"drift-the-predictions, not just the inputs" using the exact existing `DriftCalculator`**. This is directly grounded in Klaise et al.'s argument that output-distribution shift is a cheaper, earlier warning signal than joint input-feature monitoring.

## 3. Data quality validation research — beyond schema/range checks

- **"Data Validation for Machine Learning"** — Breck, Polyzotis, Roy, Zinkevich, Whang, Google, MLSys 2019 (TFX Data Validation / TFDV paper). https://research.google/pubs/data-validation-for-machine-learning/ ; PDF at https://mlsys.org/Conferences/2019/doc/2019/167.pdf. Key research contributions beyond simple range checks:
  1. **Schema inference + schema evolution with "relaxation" workflow**: rather than a human writing a static schema, TFDV *infers* an initial schema from training data statistics (this maps directly to skyulf's "fit-time JSON artifact" philosophy already), then on each new batch computes **anomaly-severity-scored deviations** (not just pass/fail) — e.g., a new categorical value appearing in 0.01% of rows is a low-severity anomaly, one appearing in 30% of rows is high-severity. This graduated severity (rather than binary pass/fail) is the main differentiator vs. naive expectation libraries.
  2. **Training/serving skew detection**: TFDV explicitly computes statistics on *both* the training dataset and a sample of live serving requests, and diffs the two distributions — catching bugs where the serving-time feature pipeline diverges from the training-time pipeline (a very common, hard-to-catch bug class: e.g., a null-handling difference between batch training code and online serving code).
     - **Direct fit for skyulf:** Since skyulf-core's preprocessing artifacts are JSON and versioned, and the *same* pipeline JSON is presumably replayed at inference time (this should be verified against skyulf's `pipeline.py`), skyulf may already have less training/serving skew risk than typical hand-written serving code — but this is worth an explicit **regression test class**: "replay stored fit-time artifact against a held-out slice of the *original* training data and assert output-statistics equality" as a CI-time skew guard, rather than a production monitoring feature. This is cheap and structurally aligned with skyulf's existing test suite (`skyulf-core/tests/test_artifact_snapshots.py` already does snapshot testing of artifacts).
  3. **Per-feature anomaly types are enumerable and typed** (missing feature, unexpected string values, out-of-range float, unexpected feature type, high fraction of new values) — this taxonomy is more granular than a single "drift_detected: bool", and their production evidence section shows most caught production bugs were **schema anomalies (new/missing columns, type changes)**, not statistical drift — i.e., **the boring schema-level checks caught more real incidents than the fancy statistical-distance checks did**. This is worth noting given prior research already flagged "need schema-drift via Pandera-style capture" — TFDV's own production evidence *validates* that this is the highest-value check, ahead of PSI/KS.
  - **Effort:** M for graduated anomaly severity (skyulf's `ColumnDrift.drift_detected` is currently boolean; adding a severity score is a moderate but valuable enhancement) + S for training/serving-skew CI regression test (reuses existing snapshot-test infra).

- **"Automating Large-Scale Data Quality Verification"** — Schelter, Lange, Schmidt, Celikel, Biessmann, Grafberger, Amazon, VLDB 2018 (the Deequ paper). https://www.vldb.org/pvldb/vol13/p3335-schelter.pdf (paper landing page; full PDF via VLDB proceedings). Key ideas beyond range/null checks:
  1. **Constraint suggestion from data profiles** — rather than a human manually writing every `expect_*` rule, Deequ profiles a dataset and *automatically suggests* a set of constraints (e.g., "this column is 99.9% non-null historically, suggest `isComplete`"; "this column has ≤5 distinct values historically, suggest `isContainedIn`"). This maps well onto skyulf's existing fit-time artifacts: e.g. `SimpleImputerArtifact.missing_counts`/`total_missing` and `IQRArtifact.bounds` are *already* exactly the statistics needed to auto-suggest `expect_no_nulls`/`expect_value_range` calls — skyulf could **auto-generate `expect.py` calls directly from the fit-time artifacts it already produces**, with zero new statistics computation. This is a very natural, low-effort differentiation: "your pipeline's own preprocessing artifacts become your data-quality contract" — tighter integration than Deequ/Evidently/Great Expectations offer, since those are bolt-on separate profiling steps disconnected from the training pipeline's own fitted parameters.
  2. **Incremental/streaming quality metric computation** using algebraic states (mergeable summary statistics) so quality checks scale to large data without full rescans — less relevant to skyulf's current batch/pandas-polars scale, but worth flagging if skyulf later targets streaming ingestion.
  - **Effort:** S (constraint auto-suggestion from existing artifacts is largely a code-generation/mapping exercise, not new algorithms) — **high-leverage, low-effort** finding.
  - **Maintained library:** Deequ has PyDeequ (PySpark-only, Amazon-maintained) — not directly embeddable given skyulf's pandas/polars engine architecture, but the *design pattern* (profile → constraint suggestion → verification) is the reusable idea, not the library itself.

**Verdict:** Two very actionable ideas: (a) TFDV's evidence that **schema-level anomalies catch more real incidents than statistical drift** (validates and reinforces the already-planned Pandera-style schema capture, don't deprioritize it in favor of fancier stats), and (b) Deequ's **constraint-suggestion-from-profile** pattern, which skyulf can implement almost for free since the fit-time JSON artifacts already contain the needed statistics (`missing_counts`, `bounds`, etc.).

## 4. Reproducibility in ML pipelines — beyond artifact/pickle versioning

- **"Improving Reproducibility in Machine Learning Research (A Report from the NeurIPS 2019 Reproducibility Program)"** — Pineau, Vincent-Lamarre, Sinha, Larivière, Beygelzimer, d'Alché-Buc, Fox, Larochelle, JMLR 2020 / arXiv:2003.12206 (642 citations). Focused on research reproducibility, but the **Machine Learning Reproducibility Checklist** they introduced generalizes cleanly to production pipelines. The checklist's non-obvious dimensions **beyond artifact/model versioning**:
  1. Exact description of **train/validation/test split methodology** (not just "we split the data" — the specific random seed, stratification method, and whether splits are fixed across experiment runs). Skyulf's `SplitArtifact` (`skyulf-core/skyulf/core/artifacts.py:496-506`) does capture `test_size`, `random_state`, `stratify` — this is already good practice; worth confirming it's surfaced prominently in any "reproducibility report" UI rather than buried.
  2. **Number of evaluation runs / variance reporting**, not single-run point estimates — a very commonly missing piece: reporting a single accuracy number without confidence intervals across seeds. For an enterprise-facing platform, offering "run this pipeline N times with different seeds and report variance" as a first-class reproducibility feature would be a meaningful differentiator, because it directly operationalizes the checklist's most-violated item (per Pineau et al.'s own compliance audit data, variance/multiple-run reporting was among the least-followed checklist items even after being made a submission requirement).
  3. **Full hyperparameter search space disclosure**, not just the final chosen hyperparameters — i.e., capturing what *range* of hyperparameters was searched (not just the winner). Skyulf's `hyperparameters/_tuning` module presumably already has a search-space config; the reproducibility angle is to make sure the **full search space + search budget** (not just best params) is part of the persisted, versioned artifact — this is subtly different from what "hyperparameter versioning" usually means (which is often just "store the winning config").
  - **Effort:** S for surfacing existing split/seed metadata prominently; M for "run N seeds, report variance" as a pipeline execution mode (requires re-running fit multiple times — compute cost, not code complexity).
  - **Differentiation:** MLflow tracks individual run parameters but doesn't enforce/template a reproducibility-checklist-style report; this would be a concrete, evidence-based feature ("Reproducibility Score" derived from a published, citable checklist) rather than an arbitrary in-house checklist.

**Verdict:** The multi-seed variance-reporting idea is the most novel, concretely actionable item here — grounded in a well-cited, checklist-driven paper rather than "pickle versioning is bad" (already known).

## 5. Enterprise/production ML pain points — updates to "Hidden Technical Debt"

- **"Operationalizing Machine Learning: An Interview Study"** — Shankar, Garcia, Hellerstein, Parameswaran, UC Berkeley, arXiv:2209.09125 (2022; semi-structured interviews with 18 MLEs across chatbots, autonomous vehicles, finance). This is the closest available 2023-era successor in spirit to "Hidden Technical Debt in Machine Learning Systems" (Sculley et al. 2015) — it identifies **three governing variables for successful production ML**: **Velocity** (iteration speed), **Validation** (confidence that a model change is actually an improvement before/during rollout), and **Versioning** (tracking of data/model/code artifact lineage together, not separately).
  - Their interview data surfaces concrete **anti-patterns** directly relevant to skyulf's roadmap:
    - MLEs frequently **cannot trust their monitoring dashboards** because metrics are computed inconsistently between training-time evaluation and production monitoring code (echoes TFDV's training/serving skew point above, but from a qualitative/organizational angle rather than a systems angle) — reinforcing that a **single shared evaluation/metrics code path** used both at training and monitoring time (which skyulf's `modeling/_evaluation` module could enforce, since it's already a first-class shared module, not duplicated logic) is a genuine structural advantage worth leaning into and marketing.
    - Interviewees report that **model validation before deployment is mostly manual and ad hoc** ("eyeballing dashboards") rather than a codified promotion gate — suggesting an opportunity for skyulf's model registry to support a **codified, JSON-artifact-backed "promotion gate" check** (e.g., "new model's evaluation metrics artifact must beat current live model's metrics artifact by threshold X, and drift-vs-training-reference must be below threshold Y") as an explicit registry feature, rather than a human-eyeballed approval step. This connects deployment gating directly to the drift/evaluation artifacts already computed.
  - **Effort:** M (codified promotion-gate logic is new registry logic, but consumes existing evaluation/drift artifact JSON rather than requiring new metric computation).
  - **Differentiation:** This is a genuinely different feature framing than MLflow's manual "stage transition" model registry UX — an **evidence-driven automatic gate** informed directly by interview-study findings about what actually fails in practice (manual, inconsistent promotion decisions).

- **"Machine Learning Operations (MLOps): Overview, Definition, and Architecture"** — Kreuzberger, Kühl, Hirschl, arXiv:2205.02302 (2022/2023, widely cited MLOps reference architecture survey). Useful primarily as a **taxonomy/checklist cross-reference** (their reference architecture enumerates: feature store, source control, model registry, workflow orchestration, model serving, monitoring) to sanity-check skyulf's roadmap coverage — no single novel finding beyond confirming registry+monitoring+versioning are the standard three-legged stool, which skyulf is already targeting. Not independently actionable beyond validating prioritization; no new specific technique to extract.

**Verdict:** Shankar et al. (2022) is the most valuable qualitative finding — it validates that **codified, artifact-driven deployment gating** (not just a bigger monitoring dashboard) addresses a real, interview-documented pain point, and gives skyulf's model-registry limitation (only one "live" model) a research-backed argument for *why* the fix matters: manual, ad hoc promotion is a named anti-pattern in real MLE workflows.

## 6. Explainability/audit-trail requirements for regulated industries

Searches for recent (2023-2025) papers specifically enumerating **audit/explainability requirements for regulated (finance/healthcare) ML platforms** did not surface a strong, directly-on-point peer-reviewed systems paper beyond the general monitoring/explainability paper already cited (Klaise et al., arXiv:2007.06299, which does briefly address counterfactual explanations as an actionability/audit mechanism for production models, but is not finance/healthcare-specific). I was not able to find (within this search budget) a rigorous, well-cited 2023-2025 paper specifically surveying regulated-industry ML audit requirements as opposed to general AI-regulation commentary (e.g. EU AI Act discussion pieces, which are policy documents rather than research papers with concrete technical prescriptions).

**Honest gap:** This sub-topic returned weaker results than the others. What Klaise et al. (arXiv:2007.06299) does offer, generically applicable to regulated contexts: **counterfactual explanations logged alongside every prediction** (not just feature-importance snapshots) are argued to be more actionable/auditable for an end-user contesting a decision (e.g., loan denial) than a global SHAP summary, because they answer "what would need to change for a different outcome" — directly relevant to adverse-action-notice requirements in US lending (ECOA/Reg B) and similar "right to explanation" framings in GDPR/EU contexts. Skyulf already has SHAP-based explainability (`skyulf-core/skyulf/modeling/_explainability/shap_explanation.py`) — the actionable idea is to **log a counterfactual alongside SHAP values for individual flagged predictions in the audit trail**, not to replace SHAP.
- **Effort:** M (counterfactual generation is more compute-intensive than SHAP and needs a library like `alibi` or `dice-ml`).
- **Suggested follow-up search:** a dedicated round specifically on "adverse action notice" / "Regulation B" / "SR 11-7 model risk management" technical requirements papers, and FAccT/AIES conference proceedings 2023-2025, would likely yield more regulated-industry-specific systems papers than general arXiv search did here.

## Cross-references / how these connect

- Sections 1 and 2 both build on skyulf's **existing** `DriftCalculator` (`skyulf-core/skyulf/profiling/drift.py`) — section 2's prediction-drift idea is a zero-new-code reuse of section 1's infrastructure.
- Sections 3's Deequ-style auto-suggestion and TFDV's schema-anomaly evidence both point to the **same underlying asset**: skyulf-core's existing fit-time `TypedDict` artifacts (`skyulf-core/skyulf/core/artifacts.py`) already contain the statistics (`missing_counts`, `bounds`, `categories`) needed to drive both schema-drift detection (already planned) and constraint auto-suggestion (newly identified here) — these should probably be designed together, not as separate features, since they consume the same artifact fields.
- Section 5's "codified promotion gate" is the most direct lever to fix the known model-registry limitation (single live model) — it reframes that fix from "just allow multiple live models" to "allow multiple live models **gated by an artifact-driven promotion check**," which is a stronger, evidence-backed product story.

## Top 5 picks (ranked by actionability × effort)

1. **[S effort] Drift-the-predictions using the existing `DriftCalculator`.** Apply skyulf-core's current PSI/KS/Wasserstein/KL drift machinery to the model's *prediction* distribution (not just input features), storing a reference prediction distribution at model-registration time. Zero new statistical code — purely a wiring/product change. Grounded in: Klaise et al., "Monitoring and Explainability of Models in Production," arXiv:2007.06299 (2020).

2. **[S effort] Auto-suggest data-quality expectations directly from existing fit-time artifacts.** Skyulf's `SimpleImputerArtifact.missing_counts`, `IQRArtifact.bounds`, etc. already contain exactly the statistics needed to auto-generate `expect_no_nulls`/`expect_value_range` calls in `profiling/expect.py` — no new profiling pass required. Grounded in: Schelter et al., "Automating Large-Scale Data Quality Verification" (Deequ), VLDB 2018, https://www.vldb.org/pvldb/vol13/p3335-schelter.pdf.

3. **[M effort] Codify a JSON-artifact-driven deployment "promotion gate"** (new model's evaluation-metric artifact must beat live model's by threshold X, and drift-vs-training-reference must stay under threshold Y) rather than manual dashboard-eyeballing before promotion — reframes the known "one live model" limitation as an evidence-based gating feature. Grounded in: Shankar et al., "Operationalizing Machine Learning: An Interview Study," arXiv:2209.09125 (2022) — validation-as-anti-pattern findings.

4. **[M effort] Multivariate/joint drift + "typifying exemplar" surfacing**, reusing existing fitted scaler/PCA-like artifacts for dimensionality reduction rather than fitting new detectors from scratch; wrap or reference `alibi-detect` for the MMD/classifier-based two-sample test rather than reimplementing. Grounded in: Rabanser, Günnemann, Lipton, "Failing Loudly: An Empirical Study of Methods for Detecting Dataset Shift," NeurIPS 2018 / arXiv:1810.11953.

5. **[M effort] Multi-seed variance reporting as a first-class reproducibility feature** ("run pipeline N times with different seeds, report variance"), operationalizing the most commonly-violated item in the peer-reviewed NeurIPS reproducibility checklist — a citable, evidence-backed "Reproducibility Score" rather than an arbitrary in-house metric.
